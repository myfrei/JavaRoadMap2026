# Лекция: Java Memory Model и happens-before

> Java Spring · Модуль 7 — Многопоточность в Java · [⬅ К содержанию трека](../README.md)

## Введение

Вы написали: сначала `a = 1`, потом `b = 2`. Кажется очевидным, что именно в таком порядке всё и
выполнится. Но это иллюзия. Компилятор Java, JIT и сам процессор имеют право **переставлять**
инструкции и кэшировать значения в регистрах ядра ради скорости — и в однопоточной программе вы
этого не заметите. А в многопоточной другой поток может увидеть `b == 2`, но `a` всё ещё `0`.

**Java Memory Model (JMM)** — это контракт, который описывает, какие переупорядочивания возможны и
при каких условиях один поток гарантированно увидит запись другого. Центральное понятие здесь —
**happens-before**. Это самая «теоретическая» лекция модуля, но именно она объясняет, почему
`volatile` и `synchronized` из лекции 2 действительно работают. Давайте разберёмся.

## Зачем нужна модель памяти

Почему вообще запись одного потока может быть не видна другому? Две причины:

1. **Переупорядочивание (reordering).** Компилятор и CPU меняют порядок независимых инструкций для
   оптимизации. В одном потоке результат тот же; между потоками — нет.
2. **Кэши ядер.** У каждого ядра свой кэш. Поток записал значение в кэш своего ядра, а другой поток
   на другом ядре всё ещё читает старое из своего.

```
   Ядро 1 (Thread A)            Ядро 2 (Thread B)
   ┌──────────────┐             ┌──────────────┐
   │ кэш: x = 1   │             │ кэш: x = 0   │  ← B не видит запись A!
   └──────┬───────┘             └──────┬───────┘
          └──────────┬─────────────────┘
                Общая память (RAM): x = 0 / 1 ?
```

JMM не запрещает оптимизации — она задаёт **границы**: набор правил happens-before, при которых
видимость гарантирована.

## happens-before — главное правило

Определение простое: если действие **A** *happens-before* **B**, то результаты A **гарантированно
видны** в B, и A не может быть переупорядочено после B.

Важно понимать, чего happens-before **не** означает: это не про «раньше по времени». Это про
**видимость и порядок**. Два действия без связи happens-before считаются конкурентными — JMM не даёт
никаких гарантий об их взаимном порядке, и компилятор волен переставить их как угодно.

## Источники happens-before

JMM перечисляет, что именно создаёт связь happens-before. Запомните этот список — он ваш инструмент:

- **Program order** — внутри одного потока действия happens-before в порядке исходного кода.
- **Освобождение/захват монитора** — выход из `synchronized`-блока happens-before следующего входа
  в **тот же** монитор.
- **volatile** — запись в `volatile`-поле happens-before любого последующего чтения **этого же**
  поля.
- **Thread.start()** — вызов `start()` happens-before любого действия внутри запущенного потока
  (новый поток видит всё, что было до старта).
- **Thread.join()** — все действия завершившегося потока happens-before возврата из `join()`.
- **final-поля** — корректно инициализированные `final`-поля видны после завершения конструктора
  без дополнительной синхронизации.

Эти связи **транзитивны**: если A hb B и B hb C, то A hb C. На этом и строится корректный код.

## Пример reordering-бага: double-checked locking

Классика, где отсутствие `volatile` ломает всё, — ленивая инициализация singleton через
double-checked locking:

```java
class Holder {
    private static Singleton instance;        // ← БАГ: не volatile

    static Singleton get() {
        if (instance == null) {               // 1-я проверка (без блокировки)
            synchronized (Holder.class) {
                if (instance == null) {       // 2-я проверка (под блокировкой)
                    instance = new Singleton();   // ← вот здесь засада
                }
            }
        }
        return instance;
    }
}
```

Строка `instance = new Singleton()` — это **три** шага: (1) выделить память, (2) вызвать
конструктор, (3) присвоить ссылку в `instance`. JIT вправе переставить (2) и (3)! Тогда другой поток
на первой (неблокирующей) проверке увидит, что `instance != null`, и вернёт ссылку на **ещё не
сконструированный** объект — с полями по умолчанию. Получаем «невозможный» баг.

✅ Лечение — `volatile`, который запрещает это переупорядочивание и устанавливает happens-before
между записью и чтением `instance`:

```java
private static volatile Singleton instance;   // ← теперь запись видна корректно
```

> На практике проще обойтись без double-checked locking: ленивый holder-idiom
> (`static class Holder { static final Singleton I = new Singleton(); }`) безопасен за счёт гарантий
> инициализации классов, а `final` даёт видимость без `volatile`.

## Семантика volatile и safe publication

`volatile` даёт две гарантии: **видимость** (запись немедленно видна всем) и **запрет
переупорядочивания** вокруг себя. Чего он **не** даёт — атомарности составных операций (`value++`
по-прежнему небезопасен, мы говорили об этом в лекции 2).

С happens-before тесно связана **safe publication** (безопасная публикация) — как корректно «отдать»
объект другому потоку, чтобы тот увидел его полностью инициализированным. Безопасные способы:

- записать ссылку в `volatile`-поле или `AtomicReference`;
- передать через корректно синхронизированный доступ (`synchronized`);
- положить в `final`-поле (видно после конструктора);
- поместить в конкурентную коллекцию (`ConcurrentHashMap` и т. п.).

❌ Небезопасно: записать ссылку в обычное (не `volatile`) поле и читать её из другого потока без
синхронизации — он может увидеть наполовину построенный объект.

## Неизменяемость и final

Самый надёжный способ избежать всех проблем видимости — **неизменяемые** (immutable) объекты. Если
после конструктора объект не меняется, его нечему «не увидеть» и нечего переупорядочивать. `final`
здесь играет ключевую роль: JMM гарантирует, что корректно установленные `final`-поля видны другим
потокам сразу после завершения конструктора, **без** дополнительной синхронизации.

```java
final class Point {              // ← immutable: поля final, объект не меняется
    private final int x, y;      // ← видны всем потокам после конструктора, без synchronized
    Point(int x, int y) { this.x = x; this.y = y; }
    int x() { return x; }
    int y() { return y; }
}
```

✅ Иммутабельность + `final` — лучший «бесплатный» способ потокобезопасности. Java `record` ровно об
этом: все его поля `final` по определению.

## Что происходит без happens-before

Сведём интуицию в схему. Без связи happens-before между записью и чтением компилятор/CPU свободны:

```
Thread A:  a = 1;        Thread B:  if (b == 2) {        Возможный исход
           b = 2;                       print(a);  ─────▶  печатает 0 (!),
                                    }                       т.к. порядок A не гарантирован
                                                            для B без happens-before

С volatile b:  запись b=2 (release) ── happens-before ──▶ чтение b==2 (acquire)
               => всё, что было до записи b в A (включая a=1), видно в B => печатает 1
```

Именно поэтому `volatile`-флаг из лекции 2 работает: чтение флага «втягивает» все предшествующие
записи потока-писателя.

## Заключение

**Что изучено:**
- Зачем нужна JMM: компилятор и CPU переупорядочивают инструкции, а кэши ядер прячут записи.
- happens-before — главное правило: A hb B ⇒ эффекты A видны в B; связь транзитивна.
- Источники happens-before: program order, монитор, `volatile`, `start`/`join`, `final`.
- Reordering-баг в double-checked locking и его лечение через `volatile`.
- Safe publication и роль `final` и иммутабельности.

**Как применять на практике:**
- Любую передачу данных между потоками опирайте на happens-before: `volatile`, `synchronized`,
  атомики, конкурентные коллекции.
- Предпочитайте неизменяемые объекты (`record`, `final`-поля) — это снимает проблему видимости.
- Не изобретайте double-checked locking без `volatile`; лучше holder-idiom или `enum`-singleton.

**Что дальше:** соберём типичные конкурентные баги — deadlock, livelock, гонки — и научимся их
лечить и диагностировать.
