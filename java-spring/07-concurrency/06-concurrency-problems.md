# Лекция: Типичные проблемы многопоточности

> Java Spring · Модуль 7 — Многопоточность в Java · [⬅ К содержанию трека](../README.md)

## Введение

Представьте узкий коридор, где двое идут навстречу. Оба шагнули вправо, чтобы разойтись, — и снова
лицом к лицу. Шагнули влево — опять столкнулись. Они активно «работают», но никуда не двигаются. Это
**livelock**. А если бы каждый замер, ожидая, что другой пройдёт первым, и оба застыли навсегда —
это **deadlock**.

Это финальная лекция трека. Здесь мы соберём «бестиарий» конкурентных багов — deadlock, livelock,
starvation, гонки — научимся их распознавать, лечить и диагностировать через thread dump. Эти баги
коварны тем, что почти не воспроизводятся: на тестах зелено, в проде раз в неделю всё висит. Давайте
вооружимся.

## Deadlock и четыре условия Коффмана

**Deadlock** (взаимная блокировка) — потоки навсегда ждут друг друга. Возникает, только когда
**одновременно** выполнены четыре условия Коффмана:

1. **Mutual exclusion** — ресурс держит только один поток.
2. **Hold and wait** — поток держит один ресурс и ждёт другой.
3. **No preemption** — ресурс нельзя отнять силой, его отдают добровольно.
4. **Circular wait** — есть кольцо ожидания: A ждёт B, B ждёт A.

Классический пример — два потока берут два замка в **разном** порядке:

```java
Object lockA = new Object(), lockB = new Object();

// Поток 1
synchronized (lockA) {          // ← взял A
    synchronized (lockB) { }    // ← ждёт B
}
// Поток 2
synchronized (lockB) {          // ← взял B
    synchronized (lockA) { }    // ← ждёт A  => кольцо => DEADLOCK
}
```

```
   Thread 1 ── держит ──▶ lockA ◀── ждёт ── Thread 2
       │                                        │
      ждёт                                   держит
       │                                        │
       └────────▶ lockB ◀───────────────────────┘
              (кольцо ожидания: ничто не сдвинется)
```

Как избежать:
- ✅ **Единый порядок захвата.** Всегда берите замки в одном глобальном порядке (например, по
  `System.identityHashCode`). Кольцо тогда невозможно — рушится условие circular wait.
- ✅ **`tryLock` с таймаутом** (из лекции 2): не дождался — отпусти всё, что взял, и повтори. Рушит
  условие hold-and-wait.

```java
if (lock1.tryLock(1, TimeUnit.SECONDS)) {
    try {
        if (lock2.tryLock(1, TimeUnit.SECONDS)) {   // ← не дождались — выходим, не виснем
            try { /* работа */ } finally { lock2.unlock(); }
        }
    } finally { lock1.unlock(); }
}
```

## Livelock и starvation

**Livelock** — потоки не заблокированы, но крутятся вхолостую, постоянно реагируя друг на друга (как
в коридоре из введения). Типичный источник — наивная стратегия «обнаружил конфликт → откатился и
сразу повторил» у всех потоков синхронно. ✅ Лечение — рандомизированная задержка перед повтором
(backoff), чтобы потоки «разъехались».

**Starvation** (голодание) — поток в принципе мог бы работать, но другие потоки постоянно
перехватывают ресурс, и он не получает его «никогда». Причины — несправедливые блокировки или
неравные приоритеты. ✅ Лечение — честные (fair) замки: `new ReentrantLock(true)` или
`new Semaphore(permits, true)` выдают доступ в порядке очереди (FIFO).

## Race condition против data race

Эти термины часто путают, но они **разные**:

- **Data race** — два потока обращаются к одной переменной **без синхронизации**, и хотя бы одно
  обращение — запись. Это нарушение JMM на уровне памяти (см. лекцию 5). Лечится синхронизацией.
- **Race condition** — корректность зависит от **порядка/тайминга** выполнения. Может существовать
  **даже без** data race: каждая операция атомарна, но их **последовательность** неверна.

Иными словами: устранив data race (добавив `volatile`/`synchronized`), вы **не обязательно**
устраните race condition. Классический пример — следующий раздел.

## Атомарность составных операций

Самая частая логическая гонка — составное действие из нескольких атомарных шагов, между которыми
может вклиниться другой поток.

**Check-then-act** — «проверил, потом сделал». Даже с потокобезопасной map тут гонка:

```java
ConcurrentHashMap<String, User> users = ...;
if (!users.containsKey(id)) {        // ← ШАГ 1: проверка (поток мог вклиниться ПОСЛЕ)
    users.put(id, new User(id));     // ← ШАГ 2: два потока создадут двух User
}
```

✅ Лечение — **атомарная** составная операция, которую предоставляет сама коллекция:

```java
users.computeIfAbsent(id, User::new);   // ← проверка+вставка одним атомарным шагом
```

**Read-modify-write** — «прочитал, изменил, записал» (`value++` из лекции 2). ✅ Лечение — атомики
(`incrementAndGet`), `synchronized` или `compareAndSet` в цикле. Главное правило: **вся** составная
операция должна быть атомарной, а не каждый её шаг по отдельности.

## Шпаргалка: проблема → симптом → лечение

| Проблема | Симптом | Лечение |
|----------|---------|---------|
| **Deadlock** | Потоки висят навсегда, CPU 0% | Единый порядок захвата замков; `tryLock` с таймаутом |
| **Livelock** | CPU 100%, прогресса нет | Рандомизированный backoff перед повтором |
| **Starvation** | Поток «никогда» не получает ресурс | Честные (fair) `ReentrantLock`/`Semaphore` |
| **Data race** | «Невозможные» значения, флаг не виден | `volatile`/`synchronized`/атомики (happens-before) |
| **Race condition** (check-then-act) | Дубли, потерянные обновления | Атомарные составные операции (`computeIfAbsent`, CAS) |

## Диагностика: thread dump через jstack

Когда приложение «зависло», первым делом снимают **thread dump** — снимок состояния всех потоков.
Узнаём PID и снимаем дамп:

```bash
jps                      # ← список Java-процессов с их PID
jstack <PID>             # ← дамп всех потоков в консоль
```

В дампе ищите потоки в состоянии `BLOCKED` и строки `waiting to lock` / `locked`. JVM умнее: при
взаимной блокировке `jstack` напрямую печатает блок **`Found one Java-level deadlock`** с участниками
кольца — это мгновенно указывает на проблему.

```
Found one Java-level deadlock:
=============================
"Thread-1": waiting to lock monitor 0x... (object lockB), which is held by "Thread-2"
"Thread-2": waiting to lock monitor 0x... (object lockA), which is held by "Thread-1"
```

Полезные инструменты помимо `jstack`: VisualVM и JDK Mission Control (оба бесплатны) показывают
потоки и блокировки в UI; на проде дамп можно слать в логи по сигналу. ⚠️ Снимайте **несколько**
дампов с интервалом: если стек потока не меняется — он действительно завис; если меняется — это,
скорее, livelock или просто медленная работа.

## ⚠️ Почему конкурентные баги так трудно ловить

И главное предостережение трека. Конкурентные баги — **недетерминированные**: проявляются лишь при
определённом, редком чередовании потоков, которое зависит от нагрузки, числа ядер, тайминга
планировщика. Отсюда практические выводы:

- «Не воспроизводится» **не равно** «исправлено». Баг может ждать своего чередования неделями.
- Отладчик меняет тайминг и часто «лечит» гонку, пока вы смотрите (эффект гейзенбага).
- Поэтому надёжность даёт не «погонять и посмотреть», а **корректный дизайн**: иммутабельность,
  happens-before, атомарные составные операции, проверенные примитивы `java.util.concurrent`.
- Тестируйте конкурентный код под **нагрузкой** (много потоков, много итераций, прогон в цикле) и
  подключайте статический анализ (SpotBugs ловит часть гонок).

## Заключение

**Что изучено:**
- Deadlock и четыре условия Коффмана; обход через единый порядок захвата и `tryLock` с таймаутом.
- Livelock (backoff) и starvation (честные замки).
- Разница data race (память) и race condition (порядок) — устранение одного не лечит другое.
- Атомарность составных операций: check-then-act и read-modify-write, лечение через
  `computeIfAbsent`/CAS.
- Диагностика thread dump через `jps`/`jstack` и почему конкурентные баги плохо воспроизводятся.

**Как применять на практике:**
- Берите замки в одном порядке и с таймаутом; для составных действий — атомарные методы коллекций.
- При зависании снимайте несколько thread dump подряд и ищите `Found one Java-level deadlock`.
- Делайте ставку на корректный дизайн (иммутабельность, happens-before), а не на «прогнал — вроде
  работает».

**Что дальше:** на этом трек по многопоточности завершён. Вы прошли путь от первого `Thread` до
виртуальных потоков, JMM и охоты на deadlock. Лучший способ закрепить — применить знания в реальном
проекте: возьмите свой сервис, найдите общее изменяемое состояние, защитите его правильным
примитивом, прогоните под нагрузкой и снимите thread dump. Теория становится навыком только на
живом коде — удачи!
