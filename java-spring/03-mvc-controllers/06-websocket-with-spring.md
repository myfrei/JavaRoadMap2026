# Лекция: WebSocket и Spring

> Java Spring · Модуль 3 — MVC и контроллеры · [⬅ К содержанию трека](../README.md)

## Введение

Представьте, что вы общаетесь по рации старого образца: чтобы услышать собеседника, надо самому нажать
кнопку и спросить «приём?». Если он захочет сказать что-то срочное, пока вы молчите, — никак, ждите,
пока снова нажмёте кнопку. Именно так работает обычный HTTP: говорит **только клиент**, сервер лишь
отвечает на запрос.

Для чата, биржевых котировок, уведомлений и онлайн-игр это мучительно — там сервер должен сам, в любой
момент, толкать данные клиенту. Нужна не рация, а **телефонный звонок**: канал открыт, оба говорят
когда хотят. В вебе такой «звонок» — это **WebSocket**. Давайте разберём, почему обычный HTTP плох для
real-time, что такое WebSocket и как поднять чат на Spring.

## Почему обычный HTTP плох для real-time

Прежде чем перейти к WebSocket, разберём, как до него выкручивались (и иногда выкручиваются) на чистом
HTTP. Есть четыре подхода — от костыля до настоящего двунаправленного канала.

| Подход | Как работает | Минусы | Когда подходит |
|--------|--------------|--------|----------------|
| **Polling** | клиент спрашивает каждые N сек | лишние запросы, задержка | редкие обновления |
| **Long-polling** | запрос «висит», пока нет данных | держит соединения, сложно | нет WebSocket |
| **SSE** | сервер шлёт поток в одну сторону | только сервер→клиент | ленты, уведомления |
| **WebSocket** | полнодуплекс в обе стороны | сложнее инфраструктура | чат, игры, торги |

```
Polling                          WebSocket
client ──"есть?"──▶ server       client ══handshake══▶ server
client ◀──"нет"──── server                  ║ один канал ║
client ──"есть?"──▶ server       client ◀────msg──────── server  ← сервер сам шлёт
client ◀──"нет"──── server       client ─────msg───────▶ server  ← клиент тоже
client ──"есть?"──▶ server       client ◀────msg──────── server
   ❌ шум, задержки                  ✅ мгновенно, в обе стороны
```

Вывод: polling — простой костыль с задержкой и шумом; SSE хорош, когда данные идут **только** от
сервера; а WebSocket нужен, когда обе стороны должны говорить свободно.

## Что такое WebSocket

**WebSocket** — это полнодуплексный канал поверх **одного** TCP-соединения. «Полнодуплекс» значит, что
данные текут одновременно в обе стороны — как телефонный разговор.

Интересно, что WebSocket-соединение **начинается как обычный HTTP-запрос**, а затем «апгрейдится».
Клиент шлёт запрос со специальным заголовком `Upgrade`, сервер соглашается — и протокол переключается
с HTTP на WebSocket поверх той же TCP-связи. Это называется **рукопожатие** (handshake).

```bash
# Запрос-рукопожатие от клиента ← обычный HTTP, но с просьбой переключиться
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket                     # ← «давай перейдём на WebSocket»
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZQ==     # ← ключ для подтверждения

# Ответ сервера ← согласие
HTTP/1.1 101 Switching Protocols       # ← код 101: протокол переключён
Upgrade: websocket
Connection: Upgrade
```

После `101 Switching Protocols` HTTP заканчивается — дальше по этому соединению летят WebSocket-кадры
в обе стороны, пока кто-то не закроет канал. Соединение не переустанавливается на каждое сообщение, в
отличие от HTTP.

## STOMP поверх WebSocket

Сам по себе WebSocket — это «голая труба»: он передаёт байты, но не говорит, *кому* и *о чём*
сообщение. Для прикладных задач (чат с комнатами, подписки на темы) поверх него используют протокол
**STOMP** (Simple Text Oriented Messaging Protocol). Он добавляет привычную модель
«publish/subscribe»: клиенты **подписываются** на адреса-темы (destinations), а сервер **публикует**
туда сообщения.

```
                  WebSocket (транспорт, «труба»)
                            │
                            ▼
                  STOMP (поверх: команды, темы)
        ┌──────────────────┼──────────────────┐
   SUBSCRIBE /topic/chat        SEND /app/send
   (клиент слушает тему)   (клиент шлёт в обработчик)
```

Spring предоставляет встроенный брокер сообщений: клиент подписывается на `/topic/...`, а вы из кода
публикуете туда, и сообщение разлетается **всем** подписчикам. Это идеально ложится на чаты и
уведомления.

## Чат на Spring: настройка

Соберём простой чат. Сначала включим WebSocket-брокер сообщений конфигурацией.

```java
@Configuration
@EnableWebSocketMessageBroker                   // ← включаем WebSocket + STOMP
public class WebSocketConfig implements WebSocketMessageBrokerConfigurer {

    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        registry.addEndpoint("/ws")             // ← URL для рукопожатия (handshake)
                .withSockJS();                  // ← фолбэк для старых браузеров (см. ниже)
    }

    @Override
    public void configureMessageBroker(MessageBrokerRegistry registry) {
        registry.enableSimpleBroker("/topic");          // ← сюда подписываются клиенты
        registry.setApplicationDestinationPrefixes("/app");  // ← сюда шлют, чтобы попасть в @MessageMapping
    }
}
```

Разбор префиксов (это путает новичков чаще всего):

- `/ws` — единственный URL, по которому браузер делает handshake и открывает WebSocket.
- `/app` — префикс для сообщений **от клиента к вашему коду** (попадают в `@MessageMapping`).
- `/topic` — адреса, на которые клиенты **подписываются**, чтобы получать рассылку.

## Чат на Spring: контроллер

Теперь сам обработчик. WebSocket-контроллер похож на REST, но вместо `@GetMapping` — `@MessageMapping`.

```java
@Controller                                     // ← обычный контроллер, но для сообщений
public class ChatController {

    @MessageMapping("/send")                     // ← ловит сообщения с /app/send
    @SendTo("/topic/chat")                       // ← результат рассылается подписчикам /topic/chat
    public ChatMessage handle(ChatMessage in) {
        // in пришёл от клиента; вернётся всем подписчикам темы /topic/chat
        return new ChatMessage(in.author(), in.text(), Instant.now());
    }
}
```

Поток получается такой: клиент шлёт в `/app/send` → попадает в `handle` → возвращённое значение
благодаря `@SendTo` уходит всем, кто подписан на `/topic/chat`. Один написал — все увидели.

А если нужно отправить сообщение **не в ответ на запрос**, а самому (например, системное уведомление
из планировщика)? Для этого есть `SimpMessagingTemplate` — его можно внедрить куда угодно и слать в
любую тему:

```java
@Service
public class NotificationService {

    private final SimpMessagingTemplate messaging;   // ← инструмент ручной отправки

    public NotificationService(SimpMessagingTemplate messaging) {  // конструкторная инъекция
        this.messaging = messaging;
    }

    public void broadcast(String text) {
        // шлём сами, без входящего запроса от клиента ← это и есть push от сервера
        messaging.convertAndSend("/topic/chat",
                new ChatMessage("SYSTEM", text, Instant.now()));
    }
}
```

- ✅ `@MessageMapping` + `@SendTo` — для логики «получил → разослал в ответ».
- ✅ `SimpMessagingTemplate` — для инициативной отправки сервером в любой момент (то, чего HTTP не умеет).

## SockJS fallback и когда что выбирать

Не во всех средах WebSocket доступен: старые браузеры, строгие корпоративные прокси могут резать
`Upgrade`. На этот случай есть **SockJS** — библиотека, которая пытается использовать WebSocket, а
если не выходит, **прозрачно** откатывается на эмуляцию через обычный HTTP (long-polling и т.п.). Ваш
код при этом не меняется — мы уже включили это через `.withSockJS()`.

Теперь финальный выбор протокола для real-time — это решение, которое от вас ждут на собеседовании.

- ✅ **WebSocket (+STOMP)** — нужна связь в **обе** стороны: чат, онлайн-игры, совместное
  редактирование, торговые терминалы.
- ✅ **SSE** (Server-Sent Events) — данные идут **только** от сервера к клиенту: лента новостей,
  прогресс-бар, уведомления. Проще WebSocket, работает поверх обычного HTTP.
- ❌ Не тащите WebSocket туда, где хватает SSE или даже редкого polling, — он дороже в инфраструктуре
  (держит постоянные соединения, требует особой настройки балансировщиков).

Правило: **сервер→клиент** — берите SSE; **обе стороны** — берите WebSocket.

## Заключение

**Что изучено:**
- Почему обычный HTTP плох для real-time (говорит только клиент) и четыре подхода: polling, long-polling, SSE, WebSocket.
- WebSocket — полнодуплекс поверх одного TCP-соединения; начинается с HTTP-рукопожатия и `101 Switching Protocols`.
- STOMP поверх WebSocket даёт модель publish/subscribe; в Spring — `@EnableWebSocketMessageBroker`, темы `/topic`, префикс `/app`.
- Чат на `@MessageMapping` + `@SendTo`, инициативная отправка через `SimpMessagingTemplate`, фолбэк SockJS.

**Как применять на практике:**
- Для двусторонней связи (чат, игры, торги) поднимайте WebSocket+STOMP; для односторонних обновлений — более лёгкий SSE.
- Не путайте префиксы: `/ws` — handshake, `/app` — вход в `@MessageMapping`, `/topic` — подписка клиентов.
- Для push без входящего запроса внедряйте `SimpMessagingTemplate`; включайте `withSockJS()` ради совместимости.
