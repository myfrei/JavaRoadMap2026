# Лекция: gRPC и Spring

> Java Spring · Модуль 3 — MVC и контроллеры · [⬅ К содержанию трека](../README.md)

## Введение

REST с JSON — как письмо обычной почтой: читаемо, универсально, но громоздко и небыстро. А теперь
представьте служебную пневмопочту между отделами одного здания: капсула летит по трубе, формат строго
оговорён заранее, доставка мгновенная. Внутри здания это удобнее писем.

**gRPC** — такая «пневмопочта» для микросервисов. Это бинарный, контракт-first протокол поверх HTTP/2
от Google. Там, где сервисы общаются между собой сотни раз в секунду, gRPC экономит трафик и время.
Давайте разберём, чем он отличается от REST, как описывается контракт и как подключить gRPC к Spring
Boot.

## Что такое gRPC

gRPC стоит на трёх китах:

1. **HTTP/2** как транспорт — мультиплексирование (много вызовов в одном соединении), сжатие
   заголовков, двунаправленные потоки. Это быстрее, чем «запрос-ответ» HTTP/1.1 у обычного REST.
2. **Protocol Buffers (protobuf)** — бинарный формат сериализации. Компактнее и быстрее JSON, но не
   читается глазами без декодера.
3. **Контракт-first** — сначала пишется файл `.proto` с описанием сервиса и сообщений, из него
   **генерируется** код клиента и сервера. Контракт — единый источник правды.

Идея: вы вызываете удалённый метод так, будто он локальный (RPC — Remote Procedure Call), а gRPC
берёт на себя сериализацию, сеть и десериализацию.

## REST против gRPC

Это не «что лучше», а «что под какую задачу». Сравним по ключевым осям.

| Характеристика | REST + JSON | gRPC |
|----------------|-------------|------|
| **Формат данных** | Текстовый (JSON) | Бинарный (protobuf) |
| **Транспорт** | HTTP/1.1 (обычно) | HTTP/2 |
| **Контракт** | Опционально (OpenAPI) | Обязателен (`.proto`) |
| **Стриминг** | Ограниченно (SSE) | Встроенный, в обе стороны |
| **Поддержка браузером** | Полная, нативная | Нет (нужен grpc-web + прокси) |
| **Читаемость** | Высокая (глазами) | Низкая (бинарь) |
| **Скорость/размер** | Медленнее, объёмнее | Быстрее, компактнее |
| **Где применяют** | Публичные API, фронтенд | Внутренние микросервисы |

Главный вывод: REST — для **внешнего** мира (браузеры, публичные API, отладка глазами), gRPC — для
**внутреннего** общения сервисов, где важны скорость и строгий контракт.

## Контракт: файл .proto

Сердце gRPC — описание контракта. Объявляем сервис и его сообщения на языке protobuf.

```proto
syntax = "proto3";                              // ← версия синтаксиса

package user;
option java_package = "com.javaroadmap.grpc";   // ← пакет для генерируемого Java-кода
option java_multiple_files = true;

// Сервис = набор удалённых методов (RPC)
service UserService {
  rpc GetUser (UserRequest) returns (UserReply);   // ← unary: один запрос → один ответ
}

// Сообщение = структура данных. Числа — это НОМЕРА полей (а не значения!)
message UserRequest {
  int64 id = 1;                                  // ← поле №1 в бинарном формате
}

message UserReply {
  int64 id = 1;
  string name = 2;
  string email = 3;
}
```

**Важное правило:** числа после `=` — это **номера полей** в бинарном представлении, а не значения.
Менять их у уже выпущенного сообщения нельзя — сломается совместимость со старыми клиентами. Добавлять
новые поля с новыми номерами — можно. Из этого `.proto` плагин сгенерирует Java-классы `UserRequest`,
`UserReply` и базовый класс сервиса, который вы реализуете.

## Четыре вида вызовов

HTTP/2 позволяет gRPC не только «запрос-ответ», но и потоки. Всего четыре вида RPC — это ключевое
преимущество над классическим REST.

```
1. Unary (обычный)              client ──req──▶ server
                                client ◀─resp── server

2. Server streaming             client ──req──▶ server
                                client ◀─msg─── server   ← сервер шлёт поток
                                client ◀─msg─── server
                                client ◀─msg─── server

3. Client streaming             client ──msg──▶ server   ← клиент шлёт поток
                                client ──msg──▶ server
                                client ◀─resp── server   ← один ответ в конце

4. Bidirectional streaming      client ──msg──▶ server   ← оба шлют потоки
                                client ◀─msg─── server      одновременно
                                client ──msg──▶ server
                                client ◀─msg─── server
```

Где это применяют:

- **Unary** — обычный вызов (получить пользователя). 90% методов.
- **Server streaming** — подписка на ленту событий, выгрузка большого списка по частям.
- **Client streaming** — загрузка файла кусками, отправка батча телеметрии.
- **Bidi streaming** — чат, онлайн-игры, двусторонняя синхронизация.

В `.proto` потоки задаются ключевым словом `stream`:

```proto
service FeedService {
  rpc Subscribe (FeedRequest) returns (stream Event);   // ← server streaming
}
```

## Интеграция с Spring Boot

Spring Boot напрямую gRPC не поддерживает, но есть стартер `grpc-spring-boot-starter`, который
поднимает gRPC-сервер и позволяет регистрировать сервисы как Spring-бины аннотацией `@GrpcService`.

```gradle
// build.gradle ← подключаем gRPC-стартер
dependencies {
    implementation 'net.devh:grpc-spring-boot-starter:3.1.0.RELEASE'
}
```

Дальше реализуем сгенерированный базовый класс и помечаем его `@GrpcService` — Spring сам поднимет
сервер на отдельном порту (по умолчанию 9090):

```java
@GrpcService                                    // ← регистрирует gRPC-сервис как бин Spring
public class UserGrpcService extends UserServiceGrpc.UserServiceImplBase {

    private final UserService service;          // обычный Spring-сервис (Model)

    public UserGrpcService(UserService service) {   // конструкторная инъекция
        this.service = service;
    }

    @Override
    public void getUser(UserRequest request,
                        StreamObserver<UserReply> responseObserver) {
        User user = service.findById(request.getId());   // ← наша бизнес-логика

        UserReply reply = UserReply.newBuilder()         // ← собираем protobuf-ответ
                .setId(user.id())
                .setName(user.name())
                .setEmail(user.email())
                .build();

        responseObserver.onNext(reply);          // ← отправляем ответ
        responseObserver.onCompleted();          // ← закрываем вызов
    }
}
```

Разбор:

- `UserServiceGrpc.UserServiceImplBase` — сгенерированный из `.proto` класс; вы переопределяете методы.
- `StreamObserver` — канал для ответа; для unary зовём `onNext` один раз, затем `onCompleted`.
- Внутри — обычный Spring: инъекция сервисов, доступ к данным. gRPC лишь меняет «дверь», а не модель.
- ✅ gRPC-сервер живёт параллельно с REST: один порт под HTTP-API, другой под gRPC.

## Когда выбирать gRPC

Чёткие критерии, чтобы не тащить gRPC туда, где хватит REST.

- ✅ **Внутренние микросервисы** — общение сервис-сервис внутри вашей инфраструктуры.
- ✅ **Низкая латентность и высокий RPS** — бинарь + HTTP/2 экономят и трафик, и время.
- ✅ **Стриминг** — нужны потоки данных в одну или обе стороны.
- ✅ **Строгий контракт** — `.proto` как единый источник правды между командами.
- ❌ **Публичный API для браузеров** — берите REST; gRPC в браузере требует grpc-web и прокси.
- ❌ **Нужна отладка глазами / простота** — JSON читается, бинарь — нет.

Типичная зрелая система использует **оба**: REST на границе (для фронтенда и партнёров) и gRPC внутри
(между микросервисами).

## Заключение

**Что изучено:**
- gRPC — бинарный контракт-first протокол поверх HTTP/2 на Protocol Buffers; вызов удалённого метода как локального.
- REST против gRPC: текст vs бинарь, опциональный vs обязательный контракт, поддержка браузера vs её отсутствие.
- Контракт в `.proto`: сервисы, сообщения, номера полей; четыре вида вызовов (unary и три вида стриминга).
- Интеграция со Spring через `grpc-spring-boot-starter` и `@GrpcService` поверх обычной бизнес-логики.

**Как применять на практике:**
- Берите gRPC для внутреннего общения микросервисов с высоким RPS и для стриминга; REST оставьте на границе.
- Начинайте с `.proto` как с контракта; не меняйте номера полей у выпущенных сообщений.
- Реализуйте логику в обычных `@Service`, а `@GrpcService` пусть будет лишь тонкой «дверью», как контроллер в REST.

**Что дальше:** разберём последний протокол модуля — WebSocket для двунаправленной связи в реальном
времени, когда «запрос-ответ» уже не подходит.
