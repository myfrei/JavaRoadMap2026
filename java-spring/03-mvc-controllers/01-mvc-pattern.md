# Лекция: Паттерн MVC

> Java Spring · Модуль 3 — MVC и контроллеры · [⬅ К содержанию трека](../README.md)

## Введение

Представьте ресторан. Вы — посетитель (браузер). Делаете заказ официанту, он несёт его на кухню,
кухня готовит, официант приносит вам блюдо на красивой тарелке. Вы не ходите на кухню сами и не
видите, как режут лук — между вами и плитой есть слои с чёткими ролями.

Ровно так устроен **MVC** — Model-View-Controller. Это не «фишка Spring», а архитектурный паттерн
1979 года, который делит приложение на три части с разной ответственностью. Spring MVC — лишь одна
из его реализаций. Давайте разберём, кто за что отвечает и почему это разделение спасает большие
приложения от превращения в кашу.

В этом модуле мы пройдём весь путь HTTP-запроса в Spring, разберём виды контроллеров, а затем три
протокола поверх HTTP — REST, gRPC и WebSocket. Но сначала — фундамент.

## Три роли: Model, View, Controller

Вернёмся к ресторану и разложим роли по полочкам:

| Роль | Ресторан | В вебе | Отвечает за |
|------|----------|--------|-------------|
| **Controller** | Официант | Класс-обработчик запроса | Приём ввода, вызов логики, выбор ответа |
| **Model** | Кухня + ингредиенты | Данные + бизнес-логика | Что показать (состояние, правила) |
| **View** | Поданное блюдо | HTML / JSON | Как это выглядит для клиента |

Ключевая идея — **разделение ответственности** (separation of concerns):

- ✅ Controller не знает, как рисуется HTML, — он лишь говорит «покажи вот эти данные».
- ✅ Model не знает про HTTP — её можно тестировать без веб-сервера.
- ✅ View не содержит бизнес-логики — только отображение.
- ❌ Если контроллер сам собирает SQL, считает скидки и клеит HTML — это «God-объект», антипаттерн.

Аналогия с официантом тут точна: официант (controller) не готовит сам и не выращивает помидоры. Он
**координирует** — принимает заказ и решает, что вынести в зал.

## Как MVC ложится на веб

В вебе общение идёт по HTTP: клиент шлёт запрос, сервер возвращает ответ. MVC встраивается в этот
цикл естественно — каждая роль занимает своё место в потоке.

```
   HTTP-запрос
   GET /products/42
        │
        ▼
   ┌───────────────┐   1. принимает запрос, достаёт id=42
   │  Controller   │   2. просит у Model данные
   └───────┬───────┘
           │ findById(42)
           ▼
   ┌───────────────┐   бизнес-логика + доступ к данным
   │     Model     │   (сервисы, сущности, репозитории)
   └───────┬───────┘
           │ Product
           ▼
   ┌───────────────┐   3. контроллер отдаёт модель во View
   │     View      │   рендер в HTML или сериализация в JSON
   └───────┬───────┘
           │
           ▼
   HTTP-ответ (HTML / JSON)
```

Заметьте: стрелки идут в одну сторону по кругу. Контроллер — единственный, кто «дирижирует». Model и
View напрямую не общаются — это и есть слабая связанность (loose coupling), за которую мы любим MVC.

## История: Model 1 против Model 2

Чтобы оценить MVC, полезно знать, от чего ушли. В ранней Java-вебе (конец 1990-х) было два подхода.

**Model 1** — вся логика прямо в JSP-странице. Страница сама принимала запрос, лезла в базу и тут же
рисовала HTML:

```jsp
<%-- Model 1: представление + логика в одном файле ← так делать НЕ надо --%>
<%
    String id = request.getParameter("id");          // ← разбор запроса
    Product p = dao.findById(Long.parseLong(id));    // ← доступ к данным
%>
<html><body>
    <h1><%= p.getName() %></h1>                       <!-- ← вывод вперемешку -->
</body></html>
```

- ❌ Логика и разметка перемешаны — невозможно тестировать и переиспользовать.
- ❌ Любое изменение правил требует правок в HTML-файле.

**Model 2** — это и есть применение MVC к вебу. Запрос сначала попадает в контроллер (сервлет), тот
вызывает модель, кладёт результат в атрибуты и **перенаправляет** на JSP, который только отображает:

```java
// Model 2: контроллер отделён от представления ← правильный путь
public class ProductServlet extends HttpServlet {
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) {
        long id = Long.parseLong(req.getParameter("id"));
        Product p = service.findById(id);            // ← Model
        req.setAttribute("product", p);              // ← передаём данные во View
        req.getRequestDispatcher("/product.jsp")     // ← View только рисует
           .forward(req, resp);
    }
}
```

Spring MVC — прямой потомок Model 2, доведённый до автоматизма: за ручной разбор запроса, выбор view
и связывание данных отвечает фреймворк, а вы пишете только бизнес-смысл.

## Где в Spring живёт каждая часть

Теперь самое важное для практики — как три абстрактные роли отображаются на реальные классы Spring.

| Часть MVC | В Spring | Аннотации / типы |
|-----------|----------|------------------|
| **Controller** | Класс-контроллер | `@Controller`, `@RestController`, `@GetMapping` |
| **Model** | Сервисы + сущности + данные | `@Service`, `@Entity`, `org.springframework.ui.Model` |
| **View** | Шаблон или сериализатор | Thymeleaf/JSP (`ViewResolver`) или Jackson (JSON) |

Небольшое уточнение про слово «Model»: в Spring оно встречается в двух смыслах. Есть **Model как
роль** (вся доменная логика и данные) и есть интерфейс `org.springframework.ui.Model` — это просто
«сумка» для передачи атрибутов во view. Не путайте: интерфейс — лишь транспорт, а настоящая модель
живёт в сервисах и сущностях.

```java
@Controller                                  // ← это Controller
public class ProductController {

    private final ProductService service;    // ← Model (бизнес-логика)

    public ProductController(ProductService service) {  // конструкторная инъекция
        this.service = service;
    }

    @GetMapping("/products/{id}")
    public String show(@PathVariable long id, Model model) {  // ← Model тут = «сумка» атрибутов
        model.addAttribute("product", service.findById(id));  // кладём данные
        return "product";                     // ← имя View: шаблон product.html
    }
}
```

Контроллер выше — идеальный официант: достал `id`, попросил у сервиса (`Model`) товар, положил его в
сумку и назвал блюдо (`"product"`). Дальше Spring сам найдёт нужный view и отрендерит. Кто именно
доставляет запрос до этого метода — тема следующей лекции про `DispatcherServlet`.

## Заключение

**Что изучено:**
- MVC делит приложение на три роли: Controller (координатор), Model (данные и логика), View (отображение).
- Разделение ответственности даёт слабую связанность: модель тестируется без HTTP, view меняется без правки логики.
- Историю Model 1 (всё в JSP) → Model 2 (MVC в вебе), наследником которого и стал Spring MVC.
- Как роли ложатся на Spring: `@Controller`/`@RestController`, сервисы и сущности, шаблоны и Jackson.

**Как применять на практике:**
- Держите контроллеры тонкими: приняли запрос → вызвали сервис → вернули ответ. Никакого SQL и склейки HTML внутри.
- Бизнес-правила выносите в `@Service`, чтобы их можно было покрыть юнит-тестами без поднятия веб-сервера.
- Различайте «Model-роль» (домен) и интерфейс `Model` (транспорт атрибутов во view) — это частая путаница новичков.

**Что дальше:** разберём `DispatcherServlet` — единую входную дверь, через которую Spring проводит
каждый HTTP-запрос от приёма до ответа.
