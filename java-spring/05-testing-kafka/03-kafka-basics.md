# Лекция: Apache Kafka — основы для разработчика

> Java Spring · Модуль 5 — Тестирование и Kafka · [⬅ К содержанию трека](../README.md)

## Введение

Представьте корабельный **бортовой журнал**. Капитан дописывает в него записи строго одну за другой, в конец, никогда не стирая и не переписывая прошлое: «08:00 вышли из порта», «09:15 прошли маяк». Любой офицер может открыть журнал, найти нужную страницу и читать с неё, сколько угодно раз. Записи лежат, пока не истечёт срок хранения.

Apache Kafka — это такой журнал, только распределённый и для сообщений между сервисами. Технически Kafka — **распределённый append-only лог**: данные только дописываются в конец и не меняются. В прошлой статье мы выяснили, *чем* стриминг отличается от очереди. Теперь давайте разберём, *из чего* Kafka собрана, — без этих понятий не понять ни отправку, ни приём.

## Словарь Kafka: семь понятий

Вся Kafka держится на горстке терминов. Разберём их сразу, дальше будем только опираться.

| Термин | Что это |
|--------|---------|
| **broker** | сервер Kafka; несколько брокеров образуют **cluster** |
| **topic** | именованный поток сообщений (например, `orders`); логическая «тема» |
| **partition** | физический кусок topic — отдельный упорядоченный лог |
| **offset** | порядковый номер сообщения **внутри партиции** (0, 1, 2, ...) |
| **producer** | тот, кто пишет сообщения в topic |
| **consumer** | тот, кто читает сообщения из topic |
| **consumer group** | группа consumer'ов, делящих между собой партиции топика |

Запомните связку: **topic делится на partitions, в каждой partition сообщения пронумерованы offset'ами, а читают их consumer'ы, объединённые в consumer group.** Дальше — подробно про каждый узел.

## Topic и partition: тема разбита на куски

**Topic** — это логическое имя потока, например `orders`. Но физически Kafka хранит его не как один сплошной лог, а как несколько **партиций** — независимых упорядоченных логов.

```
topic "orders" (3 партиции):

  partition 0:  [ msg msg msg msg ]      offsets 0..3
  partition 1:  [ msg msg msg ]          offsets 0..2
  partition 2:  [ msg msg msg msg msg ]  offsets 0..4
```

Каждая партиция — самостоятельная «дорожка», куда producer **дописывает** сообщения в конец, а каждое сообщение получает свой **offset**. Обратите внимание: offset нумеруется **внутри партиции**, а не по всему топику. В партиции 0 и в партиции 1 есть своё сообщение с offset = 0 — это разные сообщения.

## Порядок гарантирован только внутри партиции

Вот первое правило, на котором спотыкаются новички. ⚠️ **Kafka гарантирует порядок сообщений только внутри одной партиции, но НЕ между партициями.**

Внутри партиции 0 сообщения лежат строго по порядку записи: offset 0, потом 1, потом 2 — consumer прочитает их именно так. Но если два сообщения попали в **разные** партиции, про их взаимный порядок Kafka ничего не обещает — их читают параллельно разные потоки.

```
✅ В пределах partition 0:  msg#0 → msg#1 → msg#2   (порядок строгий)
❌ Между partition 0 и 1:   порядок НЕ определён    (читаются независимо)
```

Практический вывод: если для вас важен порядок (например, все события одного заказа должны идти последовательно), нужно проследить, чтобы они попадали **в одну партицию**. Как это сделать — ровно следующий раздел.

## Ключ сообщения выбирает партицию

У каждого сообщения, кроме значения (value), может быть **ключ (key)**. Именно ключ определяет, в какую партицию попадёт сообщение, по простому правилу:

```
partition = hash(key) % число_партиций
```

Отсюда два важных следствия:

- **Одинаковый ключ → всегда одна и та же партиция.** Шлёте все события заказа `order-42` с ключом `"order-42"` — они гарантированно лягут в одну партицию и сохранят порядок.
- **Нет ключа (`key = null`) → партиция выбирается равномерно** (round-robin / sticky). Порядок между такими сообщениями не гарантирован, зато нагрузка размазывается ровно.

```java
// Ключ = id заказа: все события этого заказа идут в одну партицию → порядок сохранён
producer.send(new ProducerRecord<>("orders", "order-42", "PLACED"));
producer.send(new ProducerRecord<>("orders", "order-42", "PAID"));   // ← та же партиция, что и PLACED

// Ключа нет: сообщение уйдёт в любую партицию, порядок между ними не гарантирован
producer.send(new ProducerRecord<>("orders", null, "system heartbeat"));
```

✅ Выбор ключа — это и есть ваш рычаг управления порядком и распределением. Нужен порядок по сущности — берите её id ключом. Нужна максимальная равномерность и порядок не важен — оставляйте ключ пустым.

## Consumer group: партиции делятся между потребителями

Зачем вообще дробить topic на партиции? Ради **параллелизма чтения**. Это раскрывается через **consumer group** — группу consumer'ов с общим `group.id`, которые **делят партиции между собой**.

Правило простое: **одна партиция в каждый момент отдаётся ровно одному consumer'у внутри группы**. Kafka сама раскидывает партиции по участникам (это называется rebalancing).

```
topic "orders" (3 партиции), consumer group "order-service":

  partition 0 ──▶ consumer-1
  partition 1 ──▶ consumer-2     ← каждая партиция закреплена за одним consumer'ом
  partition 2 ──▶ consumer-1        (consumer-1 тянет две, consumer-2 одну)
```

Добавили в группу третий consumer — Kafka передаст ему одну из партиций, нагрузка разложится 1:1:1. А вот четвёртый consumer в группе из 3 партиций **останется без работы**: партиций меньше, чем потребителей.

⚠️ Отсюда потолок параллелизма: **степень параллельного чтения группы ограничена числом партиций**. Хотите масштабироваться на 10 параллельных обработчиков — нужно минимум 10 партиций. Поэтому число партиций закладывают с запасом на рост.

При этом **разные группы читают топик независимо**: и `order-service`, и `analytics` получат все сообщения целиком, каждая со своим набором offset'ов — ровно та модель pub/sub из прошлой статьи.

## Брокеры, репликация и retention

Несколько штрихов про надёжность и хранение — на уровне «знать, что это есть».

**Брокеры и репликация.** Партиции живут на брокерах, и каждая партиция реплицируется на несколько брокеров для отказоустойчивости. У каждой партиции есть один **leader** (через него идут запись и чтение) и **follower'ы**, которые копируют данные. Упал брокер-leader — один из follower'ов становится новым leader, данные не теряются. Это делается «под капотом», но объясняет, почему партиций и брокеров несколько.

```
partition 0:  leader (broker-1)  ◀── копируют ──  follower (broker-2), follower (broker-3)
              broker-1 упал → follower становится leader, чтение/запись продолжаются
```

**Retention.** В отличие от очереди, Kafka **не удаляет** сообщение после чтения. Оно лежит, пока действует политика хранения — **retention**: по времени (например, `retention.ms` = 7 дней) или по размеру лога. Пока сообщение в пределах retention, любой новый consumer может прийти и перечитать историю с нужного offset. Истёк срок — старые сегменты лога удаляются.

Подробнее про надёжность, репликацию и acks — в [официальной документации Kafka](https://kafka.apache.org/documentation/#design).

## Заключение

**Что изучено:**
- Kafka — распределённый append-only лог: данные дописываются в конец и не меняются.
- Topic делится на partitions; в каждой partition сообщения пронумерованы offset'ами.
- Порядок гарантирован только **внутри** партиции, а не между ними.
- Ключ сообщения выбирает партицию (`hash(key) % N`): одинаковый ключ → одна партиция → порядок.
- Consumer group делит партиции между потребителями (1 партиция → 1 consumer в группе); параллелизм ограничен числом партиций.
- Репликация (leader/follower) даёт отказоустойчивость; retention хранит сообщения заданный срок и позволяет реплей.

**Как применять на практике:**
- Нужен порядок по сущности — отправляйте её события с ключом = id этой сущности.
- Число партиций закладывайте с запасом: это потолок параллельной обработки в группе.
- Помните про retention: Kafka — это журнал, можно перечитать историю, а не одноразовая очередь.
