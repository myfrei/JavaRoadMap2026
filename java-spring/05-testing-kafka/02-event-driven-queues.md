# Лекция: Очереди, стриминг и Event-Driven архитектура

> Java Spring · Модуль 5 — Тестирование и Kafka · [⬅ К содержанию трека](../README.md)

## Введение

Представьте кофейню. Можно работать так: вы подходите к бариста, делаете заказ и **стоите у стойки, пока он варит** — никого больше не обслуживают, очередь замерла. Это синхронный вызов: попросил — жди ответа.

А можно иначе: вы называете заказ, кассир записывает его на стаканчик и ставит в ряд, вы отходите. Бариста берёт стаканчики по мере готовности, другие клиенты делают заказы параллельно. Кассир и бариста **развязаны** — каждый работает в своём темпе. Вот это и есть мир очередей и событий.

Вы наверняка писали сервисы, которые ходят друг к другу по REST и ждут ответа. Давайте разберём, когда такая синхронность мешает и что предлагают взамен очереди и стриминг.

## Синхронный REST против асинхронных сообщений

При синхронном REST сервис A вызывает сервис B и **блокируется**, пока B не ответит. Если B тормозит или лежит — A тоже встаёт.

```
СИНХРОННО (REST):
  A ──── request ───▶ B
  A ◀─── response ─── B      ← A всё это время ждёт; B упал → A упал

АСИНХРОННО (сообщение):
  A ──▶ [ broker ] ──▶ B     ← A отдал сообщение и сразу свободен;
                               B обработает, когда сможет
```

| Свойство | Синхронный REST | Асинхронные сообщения |
|----------|-----------------|------------------------|
| Связанность | A знает адрес B и ждёт его | A знает только брокер |
| Если получатель лёг | A падает/висит | сообщение ждёт в брокере |
| Пик нагрузки | бьёт прямо по B | брокер сглаживает (буфер) |
| Ответ | сразу, в том же вызове | позже, отдельным сообщением |
| Когда брать | нужен немедленный ответ | можно обработать потом |

Асинхронность не «лучше» — она про другое. Если пользователю нужен ответ прямо сейчас (узнать баланс), REST уместен. Если задачу можно сделать чуть позже (отправить письмо, начислить бонусы) — сообщение развязывает сервисы.

## Очередь: сообщение обслужили и убрали

Первый вид брокера — **очередь** (классика — [RabbitMQ](https://www.rabbitmq.com/tutorials)). Модель почти буквально как очередь на кассе:

1. Producer кладёт сообщение в **queue**.
2. Consumer забирает его, обрабатывает.
3. После успеха consumer шлёт **ack** (подтверждение).
4. По ack брокер **удаляет** сообщение — оно сделало своё дело и исчезло.

```
producer ──▶ [ queue: ▢ ▢ ▢ ] ──▶ consumer ──ack──▶ (сообщение удалено)
```

Ключевое: **каждое сообщение обрабатывается одним consumer и затем исчезает**. Это модель «задача → исполнитель»: распределить работу между воркерами, никто не возьмёт чужую задачу дважды. Если consumer упал, не успев прислать ack, брокер вернёт сообщение в очередь и отдаст другому.

## Стриминг: сообщение остаётся в логе

Второй вид — **лог событий / стриминг** (это [Apache Kafka](https://kafka.apache.org/documentation/)). Здесь другая физика. Сообщение пишется в **topic** как запись в журнал и **не удаляется** после чтения:

1. Producer **дописывает** сообщение в конец лога (append-only).
2. Каждое сообщение получает **offset** — порядковый номер.
3. Consumer читает с нужной позиции и **сам двигает свой offset**.
4. Сообщение **остаётся** в логе по правилу retention (например, 7 дней) — независимо от того, прочитали его или нет.

```
producer ──▶ [ topic: 0 1 2 3 4 5 ... ] ── читают независимо ──▶ consumer A (offset=5)
                  (лог не стирается)      └──────────────────▶ consumer B (offset=2)
```

Ключевое отличие от очереди: **сообщение могут прочитать много разных потребителей, каждый в своём темпе и со своей позиции**. Можно «отмотать назад» и перечитать историю. Это уже не «задача-исполнитель», а «журнал фактов», который слушает кто угодно.

## Очередь против стриминга

| Характеристика | Очередь (RabbitMQ) | Стриминг (Kafka) |
|----------------|---------------------|-------------------|
| **Судьба сообщения** | удаляется после ack | остаётся (retention) |
| **Кто читает** | один consumer забирает | много независимых читателей |
| **Перечитать историю** | нельзя | можно (отмотать offset) |
| **Позиция чтения** | хранит брокер | хранит сам consumer (offset) |
| **Главная метафора** | список задач для воркеров | журнал событий / лог |
| **Сильная сторона** | распределение работы, маршрутизация | большой поток, реплей, много потребителей |

Запомните разницу одной фразой: **очередь — это про доставку задачи исполнителю, стриминг — про публикацию факта в журнал, который слушают многие**. Дальше в модуле мы работаем именно с Kafka.

## Event-Driven: события вместо команд

На этих брокерах строят **Event-Driven архитектуру** — когда сервисы общаются не командами, а **событиями**.

- **Команда** — приказ конкретному адресату: «Сервис склада, зарезервируй товар». Отправитель знает получателя и зависит от него.
- **Событие** — констатация факта в прошедшем времени: «Заказ оформлен» (`OrderPlaced`). Отправитель **не знает**, кто это слушает, и ему всё равно.

```java
// Команда: я приказываю конкретному сервису (связанность)
inventoryService.reserve(orderId, items);     // ← знаю про склад, жду его ответа

// Событие: я просто объявляю факт (развязка)
eventPublisher.publish(new OrderPlaced(orderId, items));  // ← кто слушает — не моя забота
```

Это модель **publish/subscribe (pub/sub)**: producer публикует событие в topic, а любые заинтересованные сервисы (склад, оплата, аналитика, уведомления) подписываются и реагируют **независимо друг от друга**. Захотели добавить ещё одного подписчика (например, отдел маркетинга) — просто подключаете нового consumer, продюсера трогать не нужно.

## Плюсы и минусы: честный баланс

Event-Driven — мощный, но не бесплатный подход.

✅ **Плюсы:**
- **Развязка (decoupling)** — сервисы не знают друг о друге, только про topic. Меняете одного — остальные не трогаете.
- **Масштабируемость** — добавили consumer'ов в группу, обработка пошла параллельно (как это устроено — в [статье 3](03-kafka-basics.md)).
- **Буфер пиков** — всплеск нагрузки оседает в брокере, получатели разгребают в своём темпе и не падают.
- **Расширяемость** — новый подписчик подключается, не затрагивая существующих.

❌ **Минусы:**
- **Eventual consistency** — данные согласуются не мгновенно. Сразу после `OrderPlaced` склад мог ещё не списать товар. К этому надо проектировать UI и логику.
- **Сложнее отладка** — нет одного стек-трейса сквозь систему; путь события размазан по сервисам, нужны корреляция и трейсинг.
- **Дубликаты и порядок** — сообщение может прийти повторно или не по порядку, обработчик обязан быть идемпотентным (об этом — в [статье 5](05-kafka-listener.md)).

⚠️ Не превращайте всё подряд в события. Там, где нужен немедленный ответ и строгая консистентность (списать деньги и тут же показать результат), синхронный вызов часто проще и честнее. Event-Driven — инструмент под асинхронные, развязанные сценарии, а не замена REST везде.

## Заключение

**Что изучено:**
- Синхронный REST блокирует вызывающего и связывает сервисы; асинхронные сообщения их развязывают.
- Очередь (RabbitMQ): сообщение забирает один consumer, после ack оно удаляется — модель «задача-исполнитель».
- Стриминг (Kafka): сообщение пишется в лог с offset и остаётся (retention), читать могут многие и независимо.
- Event-Driven — общение событиями (факт в прошедшем времени), а не командами; модель pub/sub.
- Плюсы: развязка, масштаб, буфер пиков, расширяемость. Минусы: eventual consistency, сложнее дебаг, дубликаты/порядок.

**Как применять на практике:**
- Нужен немедленный ответ — REST; задачу можно обработать позже и развязать сервисы — сообщения.
- Нужно распределить задачи между воркерами — думайте про очередь; нужен журнал фактов для многих потребителей и реплей — про стриминг.
- Проектируя на событиях, сразу закладывайте идемпотентность и eventual consistency.
