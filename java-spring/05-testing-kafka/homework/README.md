# Домашка модуля 5 — Тестирование и Kafka

> Статьи модуля: [оглавление](../README.md) · Примеры кода: [`src/main/java/...`](../src/main/java/com/javaroadmap/spring/s05/)

Тема — поток платёжных событий. Заготовки лежат в
[`homework/src/main/java/.../homework/`](src/main/java/com/javaroadmap/spring/s05/homework/).
Сделай «красные» тесты ([`Mod05HomeworkUnitTest`](src/test/java/com/javaroadmap/spring/s05/homework/Mod05HomeworkUnitTest.java) —
юнит-уровень, [`Mod05HomeworkKafkaTest`](src/test/java/com/javaroadmap/spring/s05/homework/Mod05HomeworkKafkaTest.java) —
интеграционный, на встроенном брокере) зелёными. **Файлы с тестами трогать не нужно.**
Docker не нужен: тесты поднимают EmbeddedKafka внутри JVM.

## Как работать

1. Открой заготовку задания, прочитай TODO и формулировку ниже.
2. Реализуй задания по порядку — они идут по пирамиде: сначала чистая логика, потом интеграция.
3. После каждого задания запускай проверку:
   ```bash
   ./gradlew :java-spring:05-testing-kafka:homeworkTest
   ```
4. Цель — **зелёный** `homeworkTest`. Общий `./gradlew build` остаётся зелёным независимо от домашки.

## Задания (по порядку)

### 1. Валидация события — юнит-уровень (статья 01)

`PaymentValidator`

**Задача.** Реализуй `isValid`: `paymentId` не null/не пустой (после trim), `amountCents > 0`,
`status` — строго `"OK"` или `"FAILED"`. Никакого Spring — чистая функция.

**Ожидаемый результат.** Юнит-тесты проходят мгновенно и без брокера — это низ пирамиды тестов.

### 2. Продюсер (статьи 03–04)

`PaymentPublisher`

**Задача.** Сделай класс бином и отправь событие через `KafkaTemplate` в топик `payments`
с **ключом `paymentId`** — события одного платежа должны попадать в одну партицию.

**Ожидаемый результат.** Тест-консьюмер читает из `payments` запись с ключом `pay-42`
и JSON-телом события.

### 3. Консьюмер: фильтр + идемпотентность (статья 05)

`PaymentListener`

**Задача.** Сделай класс бином-консьюмером топика `payments` (groupId `hw-payments`).
В `PaymentStore` сохраняй только события со статусом `OK`. Kafka гарантирует at-least-once —
повторная доставка не должна дублировать платёж (подсказка: `store.accept` уже идемпотентен).

**Ожидаемый результат.** OK-платёж появляется в хранилище, FAILED — нет; два одинаковых
события дают одну запись.

### 4. Проекция по потоку событий (статья 02)

`PaymentSummaryService`

**Задача.** Реализуй `summarize`: по списку событий посчитай число OK, число FAILED
и сумму OK-платежей. Это суть Event-Driven: состояние — производная от потока событий.

**Ожидаемый результат.** Для (OK 100, OK 250, FAILED 999) → `Summary(2, 1, 350)`;
пустой список → нули.

## 🎓 Навыки после модуля

- Раскладываешь проверки по **пирамиде тестов**: чистая логика — юнитом, доставка — интеграционно.
- Пишешь **интеграционные тесты Kafka** на EmbeddedKafka — без Docker и внешнего брокера.
- Публикуешь события через **KafkaTemplate** и понимаешь, зачем нужен ключ сообщения.
- Пишешь **@KafkaListener** и проектируешь обработку **идемпотентной** (at-least-once — это норма, не баг).
- Понимаешь ретраи и **DLT** (разобрано в примерах модуля: `KafkaErrorHandlingConfig`).
- Мыслишь **событиями**: агрегаты и сводки — проекции потока, а не строки таблицы.
