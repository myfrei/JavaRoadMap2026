# Лекция: OAuth2 и JWT в Spring Security

> Java Spring · Модуль 4 — Конфигурация и безопасность · [⬅ К содержанию трека](../README.md)

## Введение

Представьте, что вы заселяетесь в отель. Вам не выдают мастер-ключ от всего здания и не просят пароль от
вашей домашней двери. Вам дают карту-ключ от одного номера, на срок проживания. Карта подтверждает: «этому
гостю можно в комнату 502 до пятницы» — и всё, ни больше, ни меньше.

Это и есть идея, на которой стоят **OAuth2** и **JWT**. Когда приложению нужен доступ к вашим данным в
другом сервисе, оно не выпрашивает ваш пароль — оно получает ограниченный «ключ-карту» (токен) с чётким
сроком и правами. В этой финальной статье модуля мы свяжем всё воедино: разберём проблему делегированного
доступа, роли OAuth2, поток получения токена, устройство JWT и настроим Spring Security как **resource
server**.

## Проблема делегированного доступа

Допустим, сторонний сервис «Печать фото» хочет забрать ваши снимки из облака. Как дать ему доступ?

```
❌ Наивный путь: отдать сервису ваш логин и пароль от облака
   → сервис получает ПОЛНЫЙ доступ ко всему аккаунту
   → пароль хранится у третьей стороны (утечёт — потеряете всё)
   → отозвать доступ можно только сменив пароль (и сломав всё остальное)
```

Отдавать пароль — всё равно что давать гостю мастер-ключ от отеля. **OAuth2** решает это: вместо пароля
выдаётся **токен** — ограниченный по правам и сроку. Сервис печати получит доступ только на чтение фото,
без права удалять или менять что-то ещё, и вы в любой момент отзовёте этот токен, не трогая пароль.

## Роли OAuth2

В OAuth2 участвуют четыре стороны. Разберём их на примере «Печати фото» и облака.

- **Resource owner (владелец ресурса)** — это вы, пользователь, которому принадлежат данные (фото).
- **Client (клиент)** — приложение, которое хочет доступ к данным (сервис «Печать фото»).
- **Authorization server (сервер авторизации)** — кто проверяет вас и выдаёт токены (например, Google,
  Keycloak, Okta). Это «ресепшен отеля», выдающий карты-ключи.
- **Resource server (сервер ресурсов)** — где лежат сами данные и кто пускает по токену (API облака с
  фотографиями). Это «дверь номера», читающая карту.

```
Resource Owner (вы)
       │ разрешаю доступ
       ▼
   Client (Печать фото) ──── просит токен ────▶ Authorization Server (Google/Keycloak)
       │                                                   │ выдаёт токен
       │ ◀─────────────────── токен ────────────────────── │
       │
       │ запрос с токеном
       ▼
   Resource Server (API облака) ── проверяет токен ──▶ отдаёт фото
```

Ваше Spring-приложение в этой схеме чаще всего играет роль **resource server** — оно защищает свой API и
пускает запросы, только если приложен валидный токен.

## Поток Authorization Code + PKCE

Самый распространённый и безопасный способ получить токен — **Authorization Code flow**, усиленный
расширением **PKCE** (Proof Key for Code Exchange). Он используется для веб- и мобильных приложений. Идея:
клиент сначала получает одноразовый код, а потом меняет его на токен — и делает это так, что перехват кода
бесполезен.

```
1. Client → Authorization Server:  «пользователь хочет войти»
   (заодно посылает code_challenge — хэш секрета, который знает только клиент)
        │
        ▼
2. Authorization Server  ──▶  пользователь логинится и подтверждает доступ
        │
        ▼
3. Authorization Server → Client:  одноразовый authorization code
        │
        ▼
4. Client → Authorization Server:  code + code_verifier (исходный секрет)
        │  сервер проверяет: hash(verifier) == challenge из шага 1
        ▼
5. Authorization Server → Client:  access token (и refresh token)
        │
        ▼
6. Client → Resource Server:  запрос с access token  →  данные
```

⚠️ Зачем PKCE: даже если злоумышленник перехватит `authorization code` на шаге 3, обменять его на токен он
не сможет — у него нет `code_verifier` (исходного секрета). Раньше для этого использовали client secret,
но мобильное/браузерное приложение не может хранить секрет надёжно — PKCE решает это без секрета.

## Что такое JWT

Токен, который выдаёт сервер, часто имеет формат **JWT (JSON Web Token)**. Это строка из трёх частей,
разделённых точками: `header.payload.signature`.

```
eyJhbGciOiJSUzI1NiJ9 . eyJzdWIiOiJ1c2VyNDIiLCJyb2xlIjoiQURNSU4ifQ . SflKxw...
└──── header ────────┘ └──────────────── payload ────────────────┘ └ signature ┘
```

- **Header** — метаданные: какой алгоритм подписи (`RS256`), тип токена.
- **Payload** — полезная нагрузка (claims): `sub` (кто), `exp` (когда истекает), роли. Это просто
  Base64-кодированный JSON — **не шифрование**, любой может прочитать.
- **Signature** — подпись header+payload секретным/приватным ключом сервера авторизации.

Главное свойство — **stateless**: resource server не хранит сессий. Он берёт токен, проверяет подпись
ключом authorization server — если подпись верна и срок не истёк, доверяет содержимому. Подделать токен
нельзя: без ключа правильную подпись не создать.

```
Resource Server получил токен
        │
        ▼
проверяет подпись ключом Authorization Server   ── неверна ──▶ 401 (подделка)
        │ верна
        ▼
проверяет exp (срок)                            ── истёк ───▶ 401 (просрочен)
        │ ок
        ▼
доверяет claims (sub, roles) → пускает запрос
```

## Spring Security как resource server

Самый частый сценарий — ваше API проверяет JWT, выданный внешним authorization server (Keycloak, Auth0,
Google). Spring Security делает это почти декларативно. Нужен стартер
`spring-boot-starter-oauth2-resource-server` и одна строка в конфиге.

```yaml
# application.yml — указываем, КТО выдаёт токены
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.example.com/realms/myapp   # ← адрес authorization server
```

По `issuer-uri` Spring сам найдёт публичные ключи сервера (по стандартному пути) и будет проверять ими
подпись каждого входящего JWT. Вам не нужно вручную хранить ключи — Spring их подтянет и обновит.

Теперь включаем проверку токена в `SecurityFilterChain`:

```java
@Configuration
@EnableWebSecurity
public class ResourceServerConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/public/**").permitAll()
                .anyRequest().authenticated()            // ← остальное — только с валидным JWT
            )
            .oauth2ResourceServer(oauth2 -> oauth2
                .jwt(Customizer.withDefaults())          // ← валидировать входящий JWT
            )
            .sessionManagement(s -> s
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS)   // ← без сессий: всё в токене
            );
        return http.build();
    }
}
```

Что произошло:

- `oauth2ResourceServer().jwt(...)` включает фильтр, который читает заголовок `Authorization: Bearer ...`,
  проверяет подпись и срок токена.
- `STATELESS` говорит: сессии не создаём — состояние полностью в токене (как и положено JWT).
- Дальше работают привычные правила авторизации; роли можно вытащить из claims токена.

Клиент же просто прикладывает токен к каждому запросу:

```http
GET /api/orders HTTP/1.1
Authorization: Bearer eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiJ1c2VyNDIi...    ← JWT в заголовке
```

## Безопасность токенов: на что смотреть

JWT удобен, но требует аккуратности. ⚠️ Несколько правил, которые отделяют рабочую систему от дырявой.

- ⚠️ **Короткий срок жизни access token.** Минуты, не дни. Токен украдут — окно злоупотребления должно
  быть маленьким. Для продления используют отдельный **refresh token** (живёт дольше, хранится надёжнее).
- ⚠️ **Не кладите секреты в payload.** Payload — это открытый Base64, его прочитает любой. Никаких паролей,
  номеров карт, приватных данных внутри JWT.
- ⚠️ **Храните токен с умом.** В браузере `localStorage` уязвим к XSS (чужой скрипт прочитает токен).
  Безопаснее — `HttpOnly`-кука или хранение в памяти приложения, а не в доступном JS-хранилище.
- ⚠️ **Отзыв сложен.** Stateless-токен живёт до истечения — мгновенно «выключить» его трудно. Поэтому
  короткий срок жизни важнее, чем кажется; для срочного отзыва ведут блок-листы или короткие TTL.

| Что | ✅ Хорошо | ❌ Плохо |
|---|---|---|
| Срок access token | минуты (+ refresh) | дни/недели |
| Содержимое payload | id, роли, `exp` | пароли, секреты, ПДн |
| Хранение в браузере | `HttpOnly`-кука / память | `localStorage` (XSS) |
| Передача | только по HTTPS | по HTTP открытым текстом |

## Заключение

**Что изучено:**

- OAuth2 решает делегированный доступ: вместо пароля выдаётся ограниченный токен (как карта-ключ отеля).
- Четыре роли: resource owner (вы), client (приложение), authorization server (выдаёт токены), resource
  server (защищает данные).
- Authorization Code + PKCE — безопасный поток получения токена; PKCE защищает от перехвата кода без
  client secret.
- JWT — это `header.payload.signature`; payload открыт (не шифрование), подпись гарантирует подлинность,
  токен stateless.
- Spring Security в роли resource server валидирует JWT по `issuer-uri` почти декларативно.

**Как применять на практике:**

- Для защиты API внешним провайдером поднимайте resource server: стартер + `issuer-uri` + `oauth2ResourceServer().jwt(...)`.
- Ставьте `SessionCreationPolicy.STATELESS` — JWT не нужна серверная сессия.
- Делайте access token короткоживущим, продлевайте через refresh token, не кладите секреты в payload.
- Никогда не отдавайте пароль третьим сервисам — для делегированного доступа есть OAuth2-токены.
