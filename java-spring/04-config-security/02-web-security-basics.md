# Лекция: Основы безопасности веб-приложений

> Java Spring · Модуль 4 — Конфигурация и безопасность · [⬅ К содержанию трека](../README.md)

## Введение

Представьте аэропорт. На паспортном контроле пограничник смотрит ваш паспорт и убеждается, что вы — это
действительно вы. А чуть дальше, у выхода на посадку, стюардесса смотрит ваш билет и решает, пустить ли
вас в бизнес-класс или только в эконом. Две разные проверки: первая отвечает на вопрос «кто ты?», вторая —
«что тебе можно?».

Это и есть два кита веб-безопасности: **аутентификация** и **авторизация**. Их постоянно путают, хотя
разница принципиальна. Давайте разберём их, а заодно посмотрим, какие угрозы поджидают веб-приложение и
как от них защищаться. Эта статья — фундамент: дальше мы будем настраивать Spring Security, и без этих
понятий всё превратится в магические заклинания.

## Аутентификация против авторизации

Два слова похожи, но означают разные шаги.

- **Authentication (аутентификация)** — *кто ты?* Проверка личности: логин и пароль, токен, отпечаток.
  Это паспортный контроль.
- **Authorization (авторизация)** — *что тебе можно?* Проверка прав уже известного пользователя: можно ли
  ему удалять заказы, видеть админку. Это билет в бизнес-класс.

Порядок всегда один: сначала аутентификация, потом авторизация. Нельзя проверить права, не зная, кто
перед тобой.

```
Запрос  ──▶  Кто ты?            ──▶  Что тебе можно?        ──▶  Доступ
             (authentication)        (authorization)
             паспорт ✅              билет в бизнес ✅
```

| Критерий | Authentication | Authorization |
|---|---|---|
| Отвечает на вопрос | «кто ты?» | «что тебе можно?» |
| Когда происходит | первым | после аутентификации |
| На чём основана | логин/пароль, токен | роли, права (authorities) |
| Аналогия | паспортный контроль | билет в бизнес-класс |
| HTTP-ответ при провале | `401 Unauthorized` | `403 Forbidden` |

⚠️ Запомните коды: `401` — «я не знаю, кто ты» (не аутентифицирован), `403` — «я знаю, кто ты, но тебе
сюда нельзя» (не авторизован). Их часто путают местами.

## Основные угрозы OWASP

**OWASP** (Open Worldwide Application Security Project) — некоммерческое сообщество, которое ведёт список
самых частых уязвимостей веб-приложений. Пробежимся по ключевым — не для зубрёжки, а чтобы понимать, от
чего защищает Spring Security.

- **XSS (Cross-Site Scripting)** — злоумышленник внедряет чужой JavaScript на вашу страницу (например,
  через поле комментария), и он выполняется в браузере жертвы. Защита: экранировать вывод, не доверять
  пользовательскому вводу.
- **CSRF (Cross-Site Request Forgery)** — жертва, залогиненная на вашем сайте, заходит на сайт
  злоумышленника, который от её имени тихо шлёт запрос (например, «перевести деньги»). Защита: CSRF-токен,
  который чужой сайт не знает.
- **SQL-инъекции (SQL Injection)** — пользователь подсовывает SQL-код в поле ввода, и он выполняется в
  базе. Защита: параметризованные запросы (prepared statements), никогда не склеивать SQL строками.
- **Broken Authentication** — слабая защита входа: предсказуемые сессии, пароли в открытом виде,
  отсутствие защиты от перебора. Защита: правильное хранение паролей, безопасные сессии/токены.

```java
// ❌ SQL-инъекция: пользователь введёт   ' OR '1'='1   и обойдёт проверку
String sql = "SELECT * FROM users WHERE name = '" + userInput + "'";   // ← склейка строк

// ✅ параметризованный запрос: ввод не может «вырваться» в код SQL
String sql = "SELECT * FROM users WHERE name = ?";   // ← значение подставит драйвер БД
```

## Сессии против токенов

Когда пользователь вошёл, сервер должен как-то «помнить» его между запросами (HTTP сам по себе ничего не
помнит). Есть два подхода.

- **Сессии (session)** — сервер создаёт запись о пользователе у себя в памяти/хранилище и выдаёт браузеру
  идентификатор `JSESSIONID` в куке. На каждом запросе сервер по этому id находит, кто пришёл. Состояние
  живёт **на сервере** (stateful).
- **Токены (token, обычно JWT)** — сервер выдаёт подписанный токен, в котором *уже зашита* информация о
  пользователе. Сервер ничего не хранит — просто проверяет подпись токена. Состояние живёт **в токене**
  (stateless).

```
Сессии (stateful)                         Токены (stateless)
─────────────────                         ──────────────────
Браузер: Cookie JSESSIONID=abc123         Браузер: Authorization: Bearer eyJ...
Сервер:  хранит { abc123 → user 42 }      Сервер:  ничего не хранит, проверяет подпись
```

| Критерий | Сессии | Токены (JWT) |
|---|---|---|
| Где состояние | на сервере (stateful) | в токене (stateless) |
| Масштабирование на много серверов | ⚠️ нужен общий стор сессий | ✅ любой сервер проверит подпись |
| Отзыв доступа «прямо сейчас» | ✅ удалили сессию | ⚠️ сложно (живёт до истечения) |
| Подходит для | классических веб-приложений | API, микросервисы, SPA, мобайл |

Про JWT подробно — в [статье 6](06-oauth2-jwt.md). Пока достаточно понимать сам выбор.

## Хранение паролей: только хеш

Самая частая катастрофа — хранить пароли в открытом виде. ⚠️ **Пароли никогда не хранят как есть.** При
утечке базы все аккаунты мгновенно скомпрометированы, а люди часто используют один пароль везде.

```java
// ❌ КАТАСТРОФА — пароль в открытом виде; утечка базы = слив всех аккаунтов
user.setPassword("qwerty123");

// ❌ ТОЖЕ ПЛОХО — MD5/SHA-1 быстрые и давно сломаны, ломаются перебором за секунды
user.setPassword(md5("qwerty123"));

// ✅ BCrypt — медленный по задумке (защита от перебора) + соль внутри
PasswordEncoder encoder = new BCryptPasswordEncoder();
String hash = encoder.encode("qwerty123");   // ← в базу кладём ТОЛЬКО хеш
```

Почему именно **BCrypt** (или argon2 / scrypt):

- **Медленный намеренно.** Быстрый хеш — подарок взломщику: миллиарды переборов в секунду. BCrypt
  специально тормозит подбор.
- **Соль (salt) внутри.** К каждому паролю добавляется случайная соль — два одинаковых пароля дают разные
  хеши, радужные таблицы бесполезны.
- **Проверка без расшифровки.** Хеш необратим: при входе мы хешируем введённый пароль и сравниваем хеши,
  а не «расшифровываем» сохранённый.

В Spring это и есть интерфейс `PasswordEncoder` — к нему вернёмся в [статье 3](03-spring-security-architecture.md).

## HTTPS и least privilege

Ещё два правила, без которых всё остальное бессмысленно.

**HTTPS обязателен.** Без шифрования логин, пароль и токены летят по сети открытым текстом — любой
посредник (публичный Wi-Fi, провайдер) их прочитает. HTTPS шифрует канал.

```http
http://api.example.com/login    ← ❌ пароль виден всем по пути
https://api.example.com/login   ← ✅ канал зашифрован (TLS)
```

**Least privilege (принцип наименьших привилегий).** Каждый пользователь и каждый компонент должны иметь
ровно те права, что нужны для работы — и ни одним больше. Меньше прав — меньше ущерб при компрометации.

- ✅ Обычному пользователю — только его данные; админка закрыта.
- ✅ У сервиса доступ в БД — только к нужным таблицам, а не права суперпользователя.
- ❌ «Дам пока все права, потом ограничу» — это «потом» не наступает, а дыра остаётся.

## Сводка: угроза → защита

Соберём всё в одну таблицу — это карта того, что Spring Security будет закрывать.

| Угроза | Суть | Защита |
|---|---|---|
| XSS | чужой JS на вашей странице | экранирование вывода, не доверять вводу |
| CSRF | чужой сайт шлёт запрос от имени жертвы | CSRF-токен |
| SQL Injection | SQL в поле ввода | параметризованные запросы |
| Broken Authentication | слабый вход/сессии | BCrypt, безопасные сессии/токены |
| Перехват трафика | чтение данных по пути | HTTPS (TLS) |
| Избыточные права | большой ущерб при взломе | least privilege |
| Перебор паролей | подбор пароля | медленный хеш (BCrypt) + лимиты |

## Заключение

**Что изучено:**

- Аутентификация («кто ты?») всегда предшествует авторизации («что тебе можно?»); провалы — это `401` и `403`.
- Ключевые угрозы OWASP — XSS, CSRF, SQL-инъекции, broken authentication — и базовые меры против каждой.
- Состояние пользователя хранят либо в серверной сессии (stateful), либо в токене (stateless) — у каждого свои плюсы.
- Пароли хранят только как медленный хеш (BCrypt) с солью, никогда не plaintext и не MD5/SHA-1.
- HTTPS обязателен, а права раздаются по принципу least privilege.

**Как применять на практике:**

- Различайте `401` и `403` в API — это разные ситуации и разная реакция клиента.
- Никогда не склеивайте SQL строками — только параметризованные запросы.
- Для паролей берите `BCryptPasswordEncoder`; забудьте про MD5/SHA-1 и тем более plaintext.
- Включайте HTTPS даже на «внутренних» сервисах и выдавайте минимально необходимые права.

**Что дальше:** теперь, понимая *что* мы защищаем, разберём *чем* — как устроена цепочка фильтров и
ключевые абстракции Spring Security.
