# Лекция: Hibernate изнутри: сущности и их особенности

> Java Spring · Модуль 2 — Spring Data JPA и базы данных · [⬅ К содержанию трека](../README.md)

## Введение

До сих пор Hibernate был для нас «чёрным ящиком», который как-то превращает сущности в SQL. Но именно непонимание того, что внутри, рождает самые загадочные баги: запрос ушёл, хотя вы не вызывали `save()`; или наоборот — `LazyInitializationException` там, где «всё же работало».

Представьте Hibernate как личного секретаря. Вы даёте ему объекты, он держит их в блокноте (персистентный контекст), сам замечает, что вы поменяли, и в конце рабочего дня (commit) отправляет в БД пачку изменений. Давайте откроем блокнот секретаря и посмотрим, по каким правилам он работает.

## Hibernate как реализация JPA

Сначала расставим имена по местам, потому что их путают:

- **JPA** (Jakarta Persistence API) — это *спецификация*, набор интерфейсов и аннотаций (`@Entity`, `EntityManager`, `@OneToMany`). Сам по себе JPA ничего не делает.
- **Hibernate** — самая популярная *реализация* этой спецификации. Это он генерирует SQL и общается с БД.
- **Spring Data JPA** — надстройка над JPA (см. [лекцию 1](01-spring-data-jpa-intro.md)), которая ещё и репозитории генерирует.

```
Ваш код  →  Spring Data JPA  →  JPA (спецификация)  →  Hibernate (реализация)  →  JDBC  →  БД
```

То есть когда вы вызываете `repository.save()`, под капотом Spring дёргает `EntityManager.persist()`, а его реализует Hibernate. Знание JPA переносимо; знание особенностей Hibernate спасает в проде.

## Персистентный контекст (first-level cache)

Сердце Hibernate — **персистентный контекст** (persistence context), он же кэш первого уровня (L1 cache). Это «блокнот секретаря»: набор сущностей, которыми Hibernate управляет в рамках одной транзакции. Живёт он, как правило, ровно столько, сколько длится транзакция.

```java
@Transactional
public void demo(Long id) {
    Order a = repository.findById(id).orElseThrow();   // SELECT — кладём в контекст
    Order b = repository.findById(id).orElseThrow();   // НЕТ запроса — берём из контекста!
    System.out.println(a == b);                        // true — это ОДИН И ТОТ ЖЕ объект
}
```

Разбор: в пределах одной транзакции одна и та же запись = один и тот же Java-объект. Второй `findById` не идёт в БД — Hibernate возвращает уже загруженный экземпляр из контекста. Это даёт идентичность объектов и защищает от лишних запросов.

⚠️ Важно: L1-кэш — это **не** общий кэш приложения. Он привязан к транзакции и умирает вместе с ней; другая транзакция (другой запрос пользователя) его не видит.

## Состояния сущности

Любая сущность в любой момент находится в одном из четырёх состояний. Понимать их — значит понимать, когда Hibernate пойдёт в БД, а когда нет.

```
                 new Order()
                     │
                     ▼
              ┌─────────────┐  persist() / save()   ┌──────────────┐
              │  TRANSIENT  │ ────────────────────▶ │  PERSISTENT  │ ◀── find() / query
              │ (вне БД,    │                        │ (в контексте,│
              │  Hib. не    │ ◀──────────────────── │  отслежив.)  │
              │  знает)     │     (объект собран GC) └──────┬───────┘
              └─────────────┘                               │
                     ▲                                       │ detach() / clear()
            merge()  │                                       ▼      / закрытие транзакции
                     │           ┌──────────┐         ┌──────────────┐
                     └────────── │ REMOVED  │ ◀────── │   DETACHED   │
                       remove()  │ (помечен │ remove()│ (был в БД,   │
                                 │ на DELETE)│        │  вне контекста)│
                                 └──────────┘         └──────────────┘
```

| Состояние | В персистентном контексте? | Есть строка в БД? | Изменения полей отслеживаются? |
|-----------|----------------------------|-------------------|--------------------------------|
| **TRANSIENT** | ❌ нет (создан через `new`) | ❌ нет | ❌ нет — Hibernate о нём не знает |
| **PERSISTENT** | ✅ да | ✅ да | ✅ да — dirty checking + авто-`UPDATE` |
| **DETACHED** | ❌ нет (контекст закрыт) | ✅ да | ❌ нет — изменения теряются |
| **REMOVED** | ✅ да (помечен на удаление) | ✅ да, до flush | — `DELETE` уйдёт при flush |

```java
Order o = new Order("A-1");          // TRANSIENT
em.persist(o);                       // PERSISTENT — теперь отслеживается
// ... транзакция закрылась ...       // DETACHED — изменения больше не ловятся
Order managed = em.merge(o);         // снова PERSISTENT (merge возвращает НОВЫЙ управляемый объект)
em.remove(managed);                  // REMOVED — уйдёт DELETE
```

⚠️ Тонкость `merge`: он не «прикрепляет» ваш объект обратно, а **копирует** его состояние в управляемый экземпляр и **возвращает именно его**. Дальше работайте с возвращённым объектом, а не с исходным.

## Dirty checking и автоматический flush

Вот фокус, который удивляет новичков: чтобы изменить запись, **не нужно** вызывать `save()`.

```java
@Transactional
public void rename(Long id) {
    Order order = repository.findById(id).orElseThrow();  // PERSISTENT
    order.setNumber("A-999");                             // просто меняем поле в Java
    // НЕТ вызова save()! А UPDATE всё равно уйдёт в БД при коммите.
}
```

Как это работает — **dirty checking** (проверка «грязных» сущностей): загружая объект, Hibernate запоминает снимок его полей. Перед **flush** (синхронизацией с БД) он сравнивает текущее состояние со снимком и для изменившихся полей генерирует `UPDATE` сам.

Когда происходит flush:

1. Перед коммитом транзакции (главный случай).
2. Перед выполнением JPQL-запроса, который может зависеть от несохранённых изменений.
3. При явном вызове `entityManager.flush()`.

✅ Это удобно, но требует дисциплины: случайно изменив поле управляемой сущности, вы получите `UPDATE`, даже если не собирались. Для гарантированно read-only сценариев ставьте `@Transactional(readOnly = true)` — Hibernate пропустит dirty checking.

## Lazy-проксирование и LazyInitializationException

Помните `FetchType.LAZY` из [лекции 3](03-entity-relationships.md)? Технически lazy-связь — это **прокси**: вместо реального объекта Hibernate подкладывает «заглушку», которая загрузит данные при первом обращении. Но загрузить она может, только пока **жив персистентный контекст**, то есть внутри транзакции.

```java
@Transactional(readOnly = true)
public Order load(Long id) {
    return repository.findById(id).orElseThrow();   // items — это lazy-ПРОКСИ, ещё не загружен
}                                                   // ← транзакция закрылась здесь

// где-то в контроллере, ВНЕ транзакции:
Order order = service.load(1L);
order.getItems().size();    // ❌ LazyInitializationException: контекста уже нет, грузить негде
```

Разбор ошибки: к моменту `getItems()` транзакция закрыта, контекст мёртв, прокси не может сходить в БД — отсюда исключение. Это, пожалуй, самая частая ошибка новичка в JPA. Как лечить правильно:

- ✅ Догрузить связь внутри транзакции — `JOIN FETCH` или `@EntityGraph`.
- ✅ Смаппить в **DTO** прямо в транзакционном методе (см. [лекцию 2](02-entities-and-repositories.md)) — наружу уходят простые данные, прокси не утекает.

## ⚠️ open-session-in-view: костыль, который маскирует проблему

Spring Boot по умолчанию включает **Open Session In View** (OSIV) — он держит персистентный контекст открытым на всё время обработки HTTP-запроса, в том числе при рендеринге ответа. Из-за этого `LazyInitializationException` «волшебно» исчезает: lazy-связь догружается даже в контроллере.

Звучит как спасение, но это ловушка:

- ❌ Lazy-связи незаметно подгружаются при сериализации ответа → возвращается N+1 (см. [лекцию 3](03-entity-relationships.md)), а вы об этом даже не знаете.
- ❌ Соединение с БД удерживается дольше, чем нужно, — под нагрузкой пул соединений исчерпывается.
- ❌ Граница транзакции размывается: запросы летят из слоя представления, а не из сервиса.

✅ На серьёзных проектах OSIV выключают и осознанно загружают всё нужное в сервисном слое:

```yaml
spring:
  jpa:
    open-in-view: false   # ← выключаем OSIV; lazy-данные грузим явно в @Transactional
```

После этого `LazyInitializationException` перестаёт «прощаться» и честно указывает на места, где вы забыли догрузить связь, — а это именно то, что нужно для предсказуемого SQL.

## Заключение

**Что изучено:**
- JPA — спецификация, Hibernate — её реализация, Spring Data — надстройка сверху.
- Персистентный контекст (L1-кэш) живёт в рамках транзакции и даёт идентичность объектов.
- Четыре состояния: transient → persistent → detached/removed; `merge` возвращает новый управляемый объект.
- Dirty checking сам генерирует `UPDATE` без `save()`; flush — перед коммитом.
- Lazy-связь — это прокси; обращение к ней вне транзакции даёт `LazyInitializationException`.
- OSIV прячет проблему и плодит N+1 — на проде его обычно выключают.

**Как применять на практике:**
- Все изменения делайте внутри `@Transactional`; read-only помечайте `readOnly = true`.
- Грузите lazy-связи явно (`JOIN FETCH`/`@EntityGraph`) и отдавайте DTO, а не сущности.
- Выключайте `open-in-view: false` и проектируйте загрузку данных в сервисном слое.

**Что дальше:** Hibernate — мощный, но не всесилен. Разберём, когда его «магия» мешает и пора брать в руки голый SQL через JdbcTemplate.
