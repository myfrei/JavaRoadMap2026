# Лекция: Особенности реактивного подхода

> Java Spring · Модуль 6 — Реактивный стек (WebFlux) · [⬅ К содержанию трека](../README.md)

## Введение

Представьте кол-центр, где каждый оператор, приняв звонок, обязан дождаться, пока клиент сходит за паспортом, найдёт его в другой комнате и вернётся. Всё это время оператор просто сидит с трубкой у уха — он занят, но ничего полезного не делает. Чтобы обслужить 10 000 клиентов одновременно, нужно 10 000 операторов, большинство из которых просто ждут.

Именно так работает классический сервер по модели **thread-per-request**: на каждый входящий запрос выделяется отдельный поток, и если внутри есть обращение к базе или другому сервису, поток **блокируется** в ожидании ответа. Давайте разберём, почему это становится проблемой при росте нагрузки и что предлагает взамен **реактивный подход** — асинхронность, неблокирующий I/O и backpressure. Эта статья закладывает фундамент: дальше мы возьмём Project Reactor и Spring WebFlux, но сначала важно понять, *зачем* они вообще нужны.

## Проблема: thread-per-request и блокирующий I/O

В традиционном стеке (Spring MVC на Servlet/Tomcat) под каждый HTTP-запрос берётся поток из пула. Посмотрим, что делает этот поток при типичном обращении к базе.

```java
@GetMapping("/users/{id}")
public User getUser(@PathVariable Long id) {
    User user = repository.findById(id);   // ← поток ЗАМИРАЕТ здесь на 50 мс,
                                            //   пока БД не ответит — и ничего не делает
    return user;
}
```

Пока выполняется `findById`, поток не свободен: он держится в памяти (стек ~1 МБ), но процессор им не занят — это чистый простой. Теперь масштабируем:

- Пул Tomcat по умолчанию — **200 потоков**.
- Каждый запрос в среднем ждёт I/O 100 мс.
- Как только приходит 201-й запрос при занятых потоках — он встаёт в очередь и ждёт.

Это знаменитая **проблема C10k** (10 000 одновременных соединений): потоки — дорогой и ограниченный ресурс, и наращивать их бесконечно нельзя. ⚠️ Память на стеки, переключения контекста (context switches), нагрузка на планировщик ОС — всё это растёт быстрее, чем полезная работа.

## Что такое реактивность

Реактивный подход стоит на трёх китах:

1. **Асинхронность** — мы не ждём результат на месте, а описываем, *что сделать, когда он придёт*.
2. **Неблокирующий I/O (non-blocking I/O)** — поток, отправив запрос в сеть, не замирает, а идёт обслуживать другие запросы; когда ответ готов, его подхватит свободный поток.
3. **Backpressure** — потребитель (consumer) может сказать поставщику (producer): «не присылай быстрее, чем я успеваю обрабатывать». Без этого быстрый producer завалит медленного consumer и переполнит память (подробно — в статье про backpressure).

Главная идея: **небольшое число потоков (обычно по числу ядер) обслуживает тысячи соединений**, потому что потоки не простаивают в ожидании, а постоянно заняты делом.

## Imperative vs Reactive: аналогия из жизни

Чтобы прочувствовать разницу, представьте две ситуации заказа пиццы.

**Императивный (blocking) стиль** — вы позвонили в пиццерию и стоите с трубкой у уха, слушая гудки, пока пиццу готовят и везут. Вы не можете заняться ничем другим — телефон занят, вы «заблокированы».

**Реактивный (non-blocking) стиль** — вы оформили заказ, повесили трубку и занялись своими делами. Когда пицца готова, вам приходит **смс** — и вы реагируете на неё. Один человек (поток) так может «вести» десятки заказов параллельно, потому что не стоит у телефона ради каждого.

Реактивный код — это и есть «оформить и заниматься делами, а на готовность реагировать». Вместо «дай мне `User` прямо сейчас» мы говорим «вот `Mono<User>` — обещание пользователя; когда он появится, сделай с ним вот это».

Покажем тот же сценарий в коде. Сначала — императивный сервис: каждый вызов блокирует поток, а тип результата — «готовое» значение.

```java
// БЛОКИРУЮЩИЙ стиль (Spring MVC)
public UserProfile loadProfile(Long id) {
    User user = userRepo.findById(id);          // ждём БД (поток замер)
    List<Order> orders = orderApi.fetch(id);    // ждём внешний сервис (поток снова замер)
    return new UserProfile(user, orders);       // тип результата — готовый объект
}
```

Тот же сценарий реактивно: тип результата — `Mono<UserProfile>` (обещание), а два независимых обращения можно запустить параллельно, и поток нигде не «висит».

```java
// РЕАКТИВНЫЙ стиль (Spring WebFlux)
public Mono<UserProfile> loadProfile(Long id) {
    Mono<User> user = userRepo.findById(id);    // не ждём — получаем Mono (обещание)
    Mono<List<Order>> orders = orderApi.fetch(id);
    return Mono.zip(user, orders)               // оба вызова идут ПАРАЛЛЕЛЬНО
        .map(t -> new UserProfile(t.getT1(), t.getT2()));  // соберём, когда оба придут
}
```

Обратите внимание: в реактивной версии мы не получаем `User` и `List<Order>` «на руки» — мы оперируем *обещаниями* и описываем, что с ними сделать. Детали операторов (`zip`, `map`) разберём в следующей статье; пока важна сама смена мышления — от «дай результат» к «вот обещание, отреагируй на готовность».

## Спецификация Reactive Streams

Чтобы разные библиотеки (Reactor, RxJava, Akka Streams) умели работать вместе, в Java стандартизировали **Reactive Streams** — четыре маленьких интерфейса (с Java 9 они живут в `java.util.concurrent.Flow`):

| Интерфейс      | Роль                                                                    |
|----------------|-------------------------------------------------------------------------|
| `Publisher<T>` | Источник данных — «издатель». Умеет одно: принять подписчика            |
| `Subscriber<T>`| Потребитель — реагирует на `onNext` / `onError` / `onComplete`          |
| `Subscription` | Связь между ними; через `request(n)` подписчик заказывает порцию данных |
| `Processor<T,R>`| И publisher, и subscriber одновременно (промежуточное звено)            |

Ключевой момент — `Subscription.request(n)`: именно через него реализуется backpressure. Подписчик сам диктует темп, заказывая ровно столько элементов, сколько готов обработать.

```text
            subscribe()              request(n)
Subscriber ───────────────▶ Publisher ◀──────────── Subscriber
            (я готов читать)            (пришли n штук)
   ▲                                                    │
   └──────────── onNext / onComplete / onError ─────────┘
                 (данные текут обратно по запросу)
```

✅ Project Reactor (его мы возьмём в следующих статьях) — это реализация Reactive Streams: его `Mono` и `Flux` и есть `Publisher`.

## Когда реактивность оправдана, а когда нет

⚠️ Реактивность — **не серебряная пуля**. Это мощный, но сложный инструмент, и применять его «потому что модно» — частая и дорогая ошибка. Код становится труднее писать, читать и отлаживать (стектрейсы превращаются в кашу), а порог входа в команду — выше.

**Реактивность даёт выигрыш, когда:**
- ✅ много **I/O-операций** (вызовы внешних API, БД, очередей) и высокая конкурентность — потоки перестают простаивать;
- ✅ нужен **стриминг** данных (server-sent events, бесконечные потоки, постепенная отдача);
- ✅ важна экономия потоков при десятках тысяч соединений (шлюзы, прокси, агрегаторы).

**Реактивность скорее навредит, когда:**
- ❌ задача **CPU-bound** (тяжёлые вычисления) — неблокирующий I/O тут ни при чём, выигрыша нет;
- ❌ обычный **CRUD** с умеренной нагрузкой — блокирующий Spring MVC проще, читабельнее и достаточно быстр;
- ❌ в цепочке есть хоть один **блокирующий драйвер** (классический JDBC) — он сводит весь профит к нулю (об этом — в статье про репозитории).

> 💡 С появлением **виртуальных потоков (Project Loom, Java 21+)** многие сценарии «много I/O» можно закрыть привычным блокирующим кодом почти без накладных расходов. Реактивность по-прежнему сильна там, где нужны backpressure и операторная композиция потоков данных.

## Blocking vs Reactive: сводная таблица

| Характеристика        | Blocking (Spring MVC)              | Reactive (Spring WebFlux)              |
|-----------------------|------------------------------------|----------------------------------------|
| **Модель потоков**    | thread-per-request                 | event loop, мало потоков               |
| **I/O**               | блокирующий                        | неблокирующий                          |
| **Под нагрузкой**     | поток ждёт → нужен большой пул     | поток не ждёт → горстка потоков        |
| **Тип результата**    | `User`, `List<User>`               | `Mono<User>`, `Flux<User>`             |
| **Backpressure**      | нет                                | есть (`request(n)`)                    |
| **Стектрейсы/отладка**| простые, привычные                 | сложнее, асинхронные                   |
| **Порог входа**       | низкий                             | высокий                                |
| **Где силён**         | CRUD, CPU-bound, простые сервисы   | много I/O, стриминг, высокая конкурентность |

## Заключение

**Что изучено:**
- Модель thread-per-request с блокирующим I/O тратит потоки на простой и упирается в проблему C10k.
- Реактивность = асинхронность + неблокирующий I/O + backpressure: мало потоков обслуживают тысячи соединений.
- Imperative — «ждать у телефона», reactive — «получить смс, когда готово».
- Reactive Streams (`Publisher`/`Subscriber`/`Subscription`/`Processor`) — общий стандарт; `request(n)` даёт backpressure.

**Как применять на практике:**
- Берите реактивность под I/O-bound и стриминговые сценарии с высокой конкурентностью.
- Не тащите её в простой CRUD и CPU-bound задачи — там она только усложнит код.
- Помните про блокирующие драйверы в цепочке и про виртуальные потоки как более простую альтернативу для «много I/O».

**Что дальше:** познакомимся с Project Reactor — типами `Mono` и `Flux` и их операторами, из которых строятся реактивные цепочки.
