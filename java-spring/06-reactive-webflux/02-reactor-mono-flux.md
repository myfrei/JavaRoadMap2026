# Лекция: Reactor: Mono, Flux и операторы

> Java Spring · Модуль 6 — Реактивный стек (WebFlux) · [⬅ К содержанию трека](../README.md)

## Введение

В прошлой статье мы договорились, что реактивный код — это «оформить заказ и реагировать на готовность». Но чтобы что-то «оформлять», нужны подходящие типы-обёртки. В мире Spring их даёт **Project Reactor** — библиотека, реализующая Reactive Streams и лежащая в основе WebFlux.

Представьте конвейерную ленту на фабрике. На неё кладут заготовки, по пути стоят станки (один красит, другой сверлит, третий проверяет качество), а в конце — упаковка. Лента сама по себе ничего не делает, пока её не **включат**. Reactor — это и есть такой конвейер для данных: вы описываете цепочку обработки операторами, а запускается она только при подписке. Давайте разберём два главных типа — `Mono` и `Flux` — и операторы, из которых собирается конвейер.

## Mono и Flux: 0..1 против 0..N

В Reactor есть ровно два `Publisher`-типа, и разница между ними — в количестве элементов:

- **`Mono<T>`** — поток из **0 или 1** элемента. Аналог «одного значения, которое появится позже»: один пользователь, результат сохранения, `void`-операция.
- **`Flux<T>`** — поток из **0..N** элементов (возможно, бесконечный): список товаров, лента событий, строки файла.

```java
import reactor.core.publisher.Mono;
import reactor.core.publisher.Flux;

Mono<String> one = Mono.just("Hello");              // ровно один элемент
Mono<String> empty = Mono.empty();                  // ноль элементов (аналог null, но безопасный)

Flux<Integer> few = Flux.just(1, 2, 3);             // три элемента
Flux<Integer> range = Flux.range(1, 100);           // 1..100
Flux<Long> ticks = Flux.interval(Duration.ofSeconds(1)); // бесконечный: 0,1,2,... каждую секунду
```

Правило выбора простое: ожидаете **не больше одного** результата — берите `Mono`; ожидаете **много** — `Flux`.

## ⚠️ Ничего не происходит без subscribe()

Это главная мысленная ловушка для новичка. `Mono` и `Flux` — **ленивые (lazy)**: пока на них не подписались, не выполняется *ничего*. Цепочка операторов — это лишь *рецепт*, а не само блюдо.

```java
Mono<String> mono = Mono.fromCallable(() -> {
    System.out.println("Выполняюсь!");   // ← этот код НЕ запустится...
    return "result";
});
// ...до тех пор, пока кто-то не подпишется:
mono.subscribe(value -> System.out.println("Получил: " + value));
// Только теперь в консоли появится "Выполняюсь!" и "Получил: result"
```

Запомните: **`subscribe()` — это кнопка «пуск» на конвейере**. В реальном Spring WebFlux подписку за вас выполняет фреймворк (когда возвращаете `Mono`/`Flux` из контроллера), поэтому вручную `subscribe()` в коде приложения вы почти не пишете. ⚠️ Если же вы вернули `Mono`, но забыли его вернуть/подписать — операция просто молча не выполнится.

## Холодные и горячие потоки

- **Холодный (cold) поток** — стартует заново для *каждого* подписчика. `Flux.range(1, 3)` выдаст `1,2,3` и первому подписчику, и второму, и десятому — независимо. Большинство потоков в приложениях холодные.
- **Горячий (hot) поток** — существует независимо от подписчиков и вещает «в прямом эфире». Подписался поздно — пропустил то, что уже прошло (как телетрансляция: включил телевизор — смотришь с текущего момента, а не с начала).

Пока достаточно держать в голове: данные из БД и HTTP — обычно холодные; потоки событий «здесь и сейчас» — горячие.

## Операторы: map, flatMap, filter, zip

Операторы — это «станки на конвейере». Каждый возвращает новый `Mono`/`Flux`, не меняя исходный (как у `Stream`, но асинхронно).

```java
Flux.range(1, 5)                     // 1, 2, 3, 4, 5
    .filter(n -> n % 2 == 1)         // оставить нечётные:        1, 3, 5
    .map(n -> n * 10)                // синхронно преобразовать:  10, 30, 50
    .subscribe(System.out::println);
```

- **`map`** — синхронное преобразование «элемент → элемент» (как `Stream.map`).
- **`filter`** — пропустить только подходящие элементы.

Особый и самый важный оператор — **`flatMap`**. Он нужен, когда преобразование само **асинхронное** и возвращает `Mono`/`Flux` (например, вызов другого сервиса). `map` тут дал бы `Mono<Mono<...>>` — вложенность; `flatMap` её «разворачивает».

```java
Flux<Long> userIds = Flux.just(1L, 2L, 3L);

Flux<User> users = userIds
    .flatMap(id -> userService.findById(id));   // ← findById возвращает Mono<User>;
                                                 //   flatMap подписывается и «разворачивает» его
```

✅ Запомните грубое правило: **возвращаемое значение — обычный объект → `map`; возвращаемое значение — `Mono`/`Flux` → `flatMap`**.

Чтобы **объединить** несколько независимых потоков, есть `zip` — он берёт по одному элементу из каждого и склеивает:

```java
Mono<User> user = userService.findById(1L);
Mono<List<Order>> orders = orderService.findByUser(1L);

Mono<UserProfile> profile = Mono.zip(user, orders)   // оба вызова идут ПАРАЛЛЕЛЬНО
    .map(tuple -> new UserProfile(tuple.getT1(), tuple.getT2()));
```

## Обработка ошибок

В реактивной цепочке ошибка — это сигнал `onError`, который «гасит» поток. Перехватывать его через `try/catch` бесполезно (всё асинхронно) — для этого есть операторы:

```java
userService.findById(id)
    .map(User::getEmail)
    .onErrorResume(ex -> {                       // ← перехватили ошибку, отдаём запасное значение
        log.warn("Не нашли пользователя", ex);
        return Mono.just("unknown@example.com");
    });

externalApi.fetchRate()
    .retry(3)                                    // ← при ошибке повторить запрос до 3 раз
    .onErrorReturn(BigDecimal.ZERO);             // если и после ретраев не вышло — вернуть 0
```

- `onErrorResume` — подменить ошибку *другим потоком* (запасной источник).
- `onErrorReturn` — подменить ошибку *одним значением по умолчанию*.
- `retry(n)` — повторить подписку при ошибке (полезно для нестабильной сети).

## subscribeOn и publishOn (кратко)

Иногда нужно управлять тем, на каком пуле потоков (`Scheduler`) выполняется цепочка:

- **`subscribeOn(scheduler)`** — задаёт пул для *начала* цепочки (где сработает источник). Влияет на всю цепочку вверх.
- **`publishOn(scheduler)`** — переключает пул для *последующих* операторов (вниз по цепочке).

```java
Mono.fromCallable(() -> heavyBlockingCall())     // что-то тяжёлое/блокирующее
    .subscribeOn(Schedulers.boundedElastic())    // ← вынести на пул для блокирующих задач
    .map(result -> result.trim());
```

`Schedulers.boundedElastic()` — стандартный приём «изолировать неизбежно блокирующий вызов», чтобы он не занимал потоки event loop. На старте достаточно знать, что эти операторы существуют; тонкости — отдельная большая тема.

## Marble-схема: как читать поток

Поток во времени удобно рисовать «шариками» (marbles), слева направо. Покажем цепочку `filter → map`:

```text
исходный Flux:   --1--2--3--4--5--|        ( | — сигнал onComplete )

  .filter(нечётные)
                 --1-----3-----5--|

  .map(* 10)
                 --10----30----50-|

  X вместо | означало бы onError (поток оборвался с ошибкой)
```

Такие marble-диаграммы — стандартный язык документации Reactor: ось — время, шарики — элементы (`onNext`), `|` — завершение (`onComplete`), `X` — ошибка (`onError`).

## Полный пример цепочки

Соберём всё вместе — типичный сценарий «получить заказы пользователя, обогатить и посчитать сумму»:

```java
public Mono<OrderSummary> buildSummary(Long userId) {
    return userRepository.findById(userId)                  // Mono<User>
        .switchIfEmpty(Mono.error(                          // нет пользователя → осмысленная ошибка
            new UserNotFoundException(userId)))
        .flatMapMany(user -> orderRepository                // ← Mono → Flux (много заказов)
            .findByUserId(user.id()))                       // Flux<Order>
        .filter(order -> order.status() == PAID)            // только оплаченные
        .map(Order::amount)                                 // Flux<BigDecimal>
        .reduce(BigDecimal.ZERO, BigDecimal::add)           // свернуть в одну сумму → Mono
        .map(total -> new OrderSummary(userId, total))      // упаковать результат
        .onErrorResume(ex -> Mono.just(OrderSummary.empty(userId))); // запасной вариант
}
```

Обратите внимание: тут нет ни одного `block()` и ни одного `subscribe()` — мы лишь *описали* конвейер и вернули `Mono`. Запустит его WebFlux, когда придёт HTTP-запрос.

## ⚠️ Не вызывайте block()

У `Mono`/`Flux` есть метод `block()`, который «дожидается» результата и возвращает обычное значение. Соблазнительно — но это **разрушает всю идею реактивности**: поток снова блокируется в ожидании.

```java
String email = userService.findById(id).map(User::getEmail).block();  // ❌ так НЕ надо в WebFlux
```

❌ Внутри event loop вызов `block()` может вообще выбросить исключение (`IllegalStateException`) — Reactor намеренно это запрещает. ✅ Правильно — оставаться в реактивном мире: вернуть `Mono`/`Flux` наружу и дать фреймворку подписаться. `block()` допустим лишь на «краю» — например, в простом юнит-тесте или в `main()`.

## Заключение

**Что изучено:**
- `Mono<T>` — 0..1 элемент, `Flux<T>` — 0..N; выбор зависит от количества результатов.
- Потоки ленивые: без `subscribe()` (в WebFlux его делает фреймворк) ничего не происходит.
- Холодные потоки стартуют для каждого подписчика, горячие вещают «в эфир».
- Операторы: `map`/`filter` — синхронно, `flatMap` — для асинхронных вложенных потоков, `zip` — параллельное объединение.
- Ошибки ловят `onErrorResume`/`onErrorReturn`/`retry`, а не try/catch.

**Как применять на практике:**
- Стройте бизнес-логику как цепочку операторов и возвращайте `Mono`/`Flux`, не разворачивая их раньше времени.
- Помните различие `map` vs `flatMap` — это источник львиной доли ошибок у новичков.
- Никогда не вызывайте `block()` в реактивном коде; читайте документацию по marble-диаграммам.
