# Домашка модуля 1 — IoC, DI и бины

Заготовки лежат в [`homework/src/main/java/.../homework/`](src/main/java/com/javaroadmap/spring/s01/homework/) —
по файлу на класс, TODO внутри. Сделай «красные» тесты
[`Mod01HomeworkTest.java`](src/test/java/com/javaroadmap/spring/s01/homework/Mod01HomeworkTest.java) зелёными.
**Файл с тестами трогать не нужно.**

## Как работать

1. Открой заготовку задания, прочитай TODO и формулировку ниже.
2. Реализуй задания по порядку (они идут по плану модуля).
3. После каждого задания запускай проверку:
   ```bash
   ./gradlew :java-spring:01-ioc-di-beans:homeworkTest
   ```
4. Цель — **зелёный** `homeworkTest`. Общий `./gradlew build` остаётся зелёным независимо от домашки.

## Задания (по порядку)

### 1. Внедрение зависимостей (статья 01)

`RubPriceFormatter`, `ReceiptService`

**Задача.** Сделай `RubPriceFormatter` бином, находимым component scan-ом, и реализуй
`format()` (формат `"<сумма> ₽"`). Сделай `ReceiptService` сервисом-бином, внедри в него
`PriceFormatter` **через конструктор** и реализуй `receipt()`.

**Ожидаемый результат.** Контейнер собирает связку сам: `receipt("alice", 100)` → `"Чек для alice: 100 ₽"`;
по типу `PriceFormatter` из контекста достаётся именно `RubPriceFormatter`.

### 2. Жизненный цикл бина (статья 02)

`CacheWarmup`

**Задача.** Сделай класс бином. `warmUp()` должен выполняться автоматически **после создания** бина
(`warm = true`), `shutdown()` — **при закрытии контекста** (`warm = false`, `shutDown = true`).
Вспомни, какие аннотации вешаются на init/destroy-методы.

**Ожидаемый результат.** Сразу после старта контекста `isWarm() == true`; после `context.close()`
кэш погашен и `isShutDown() == true` — без единого ручного вызова этих методов.

### 3. Java-конфигурация (статья 03)

`HomeworkConfig`, `TaxCalculator`

**Задача.** `TaxCalculator` — «чужой» класс, аннотации на него не повесить. Преврати `HomeworkConfig`
в Java-конфигурацию и объяви в ней бин `TaxCalculator` со ставкой `0.20`.

**Ожидаемый результат.** `TaxCalculator` достаётся из контекста как обычный бин: `withTax(100) == 120`.

### 4. Сервисный слой (статья 04)

`OrderStatsService`

**Задача.** Сделай класс сервисом-бином, внедри `StatsRepository` через конструктор и реализуй
`totalRevenue()`, `averageCheck()` (целочисленно; пустое хранилище → 0) и `maxAmount()` (пустое → 0).

**Ожидаемый результат.** На данных готового репозитория (100, 200, 300, 400):
выручка 1000, средний чек 250, максимум 400.

### 5. Выбор реализации и scope (статья 06)

`SequentialIdGenerator`, `FixedIdGenerator`, `ScratchBuffer`

**Задача.**
- `SequentialIdGenerator` — бин по умолчанию: при внедрении по типу `IdGenerator` выигрывает он;
  `nextId()` возвращает 1, 2, 3, …
- `FixedIdGenerator` — бин с **именем** `"fixed"`; `nextId()` всегда 42.
- `ScratchBuffer` — каждый запрос к контейнеру должен возвращать **новый** экземпляр (подбери scope).

**Ожидаемый результат.** `getBean(IdGenerator.class)` → последовательный генератор;
`getBean("fixed", ...)` → 42; два `getBean(ScratchBuffer.class)` — разные независимые объекты.

## 🎓 Навыки после модуля

- Проектируешь классы под **конструкторное внедрение**: зависимости — интерфейсы, без `new` внутри.
- Управляешь **жизненным циклом** бина: init/destroy-колбэки вместо ручной инициализации.
- Регистрируешь **сторонние классы** бинами через `@Configuration`/`@Bean`.
- Строишь **сервисный слой**: бизнес-логика в `@Service`, данные за интерфейсом репозитория.
- Разруливаешь **несколько реализаций** одного интерфейса (`@Primary`, имя бина/квалификатор)
  и осознанно выбираешь **scope** (singleton vs prototype).
