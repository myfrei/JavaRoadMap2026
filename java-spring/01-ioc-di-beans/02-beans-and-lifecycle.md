# Лекция: Бины и их жизненный цикл

> Java Spring · Модуль 1 — IoC, DI и бины · [⬅ К содержанию трека](../README.md)

## Введение

Представьте отель. Вы не строите номер сами и не убираете его после выезда — об этом заботится персонал:
подготовить комнату, выдать ключ, прибраться, а в конце освободить номер для следующего гостя. Вы просто
живёте и пользуетесь сервисом.

В Spring роль такого «персонала» играет IoC-контейнер, а роль номеров — **бины (beans)**. Бин — это
обычный Java-объект, но с важной оговоркой: его создаёт, настраивает, хранит и уничтожает контейнер, а не
вы. Давайте разберём, что именно происходит с объектом с момента «заселения» и до «выезда» — этот путь
называется **жизненным циклом бина (bean lifecycle)**. Понимание этих стадий пригодится, когда понадобится
выполнить код при старте (например, прогреть кэш) или аккуратно освободить ресурсы при завершении.

## Что такое бин

**Бин** — это объект, которым управляет Spring-контейнер: контейнер отвечает за его создание, внедрение
зависимостей, хранение в `ApplicationContext` и уничтожение.

Ключевая мысль: не каждый объект в вашем приложении — бин. Бином объект становится только тогда, когда вы
*объявили* его контейнеру. Объект, созданный вручную через `new`, бином не является — Spring о нём не знает
и зависимости в него не внедрит.

## Как объявить бин: два пути

Есть два основных способа сказать контейнеру «сделай это бином».

**Способ 1 — стереотипные аннотации (component scanning).** Вешаете аннотацию на класс, и Spring при
сканировании сам его подхватит.

```java
@Service   // ← стереотип: «это бин, причём сервис»
public class PriceCalculator {
    public BigDecimal calculate(Order order) { /* ... */ }
}
```

Стереотипы — это специализации `@Component`:

- `@Component` — общий бин;
- `@Service` — бизнес-логика;
- `@Repository` — слой доступа к данным;
- `@Controller` / `@RestController` — веб-слой.

Технически они почти эквивалентны, но несут *семантику* (роль класса) и иногда дополнительное поведение
(например, `@Repository` включает трансляцию исключений БД).

**Способ 2 — фабричный метод `@Bean` в `@Configuration`.** Когда класс не ваш (из библиотеки) и аннотацию
на него не повесить, или создание требует логики.

```java
@Configuration
public class AppConfig {

    @Bean   // ← возвращаемый объект станет бином с именем "objectMapper"
    public ObjectMapper objectMapper() {
        ObjectMapper mapper = new ObjectMapper();   // ← класс из библиотеки Jackson
        mapper.findAndRegisterModules();
        return mapper;   // ← контейнер возьмёт этот объект под управление
    }
}
```

Разница простая: `@Component` и друзья — для *ваших* классов (контейнер создаёт их сам), а `@Bean` — когда
объект создаёте *вы* внутри метода, а контейнер лишь регистрирует результат.

| Критерий | Стереотипы (`@Component`/`@Service`/…) | `@Bean` в `@Configuration` |
|---|---|---|
| На чём аннотация | на классе | на методе |
| Кто создаёт объект | Spring (вызывает конструктор) | вы (внутри метода) |
| Подходит для своих классов | ✅ да | ✅ да |
| Подходит для классов из библиотек | ❌ нельзя добавить аннотацию | ✅ да |
| Логика при создании | ⚠️ ограниченно | ✅ любая |
| Находится через `@ComponentScan` | ✅ да | ⚠️ нужен импорт конфигурации |

## Как контейнер создаёт бин

Когда Spring решает создать бин, по умолчанию он вызывает его конструктор. Если конструктор требует
другие бины — контейнер сначала создаёт их (рекурсивно), а затем передаёт в конструктор. Так строится
весь граф зависимостей.

```java
@Service
public class OrderService {
    private final PriceCalculator calculator;   // ← зависимость

    public OrderService(PriceCalculator calculator) {   // ← Spring сначала создаст PriceCalculator,
        this.calculator = calculator;                    //   потом вызовет этот конструктор
    }
}
```

Но создание конструктором — лишь *первый* шаг. Дальше начинается самое интересное.

## Полный жизненный цикл бина

Между «объект создан» и «объект готов к работе» Spring проходит несколько фаз. Вот полный путь:

```
                    ЖИЗНЕННЫЙ ЦИКЛ БИНА

  1. Instantiate              вызов конструктора (объект создан, но пустой)
            │
            ▼
  2. Populate dependencies    внедрение зависимостей (@Autowired, конструктор)
            │
            ▼
  3. *Aware-интерфейсы        BeanNameAware, ApplicationContextAware и т.п.
            │                 (бин узнаёт детали об окружении)
            ▼
  4. BeanPostProcessor        postProcessBeforeInitialization(...)
     .before                  (хук ДО инициализации)
            │
            ▼
  5. Инициализация            @PostConstruct → InitializingBean.afterPropertiesSet()
            │                 → init-method из @Bean
            ▼
  6. BeanPostProcessor        postProcessAfterInitialization(...)
     .after                   (хук ПОСЛЕ; здесь часто создаются прокси: @Transactional, AOP)
            │
            ▼
  ┌────────────────────┐
  │  7. БИН ГОТОВ       │ ◀── используется приложением
  │     (in use)        │
  └─────────┬──────────┘
            │  (при остановке контекста)
            ▼
  8. Уничтожение              @PreDestroy → DisposableBean.destroy()
                              → destroy-method из @Bean
```

Запоминать наизусть все восемь стадий не нужно. Важно уловить логику: **сначала объект создаётся,
потом наполняется зависимостями, потом инициализируется, работает и в конце аккуратно уничтожается.**
Шаги 4 и 6 (`BeanPostProcessor`) — это точки, где Spring «оборачивает» ваши бины: именно на шаге 6
появляется прокси для `@Transactional` или кэширования.

## @PostConstruct и @PreDestroy на практике

Чаще всего вам понадобятся всего две точки: «сделать что-то сразу после готовности» и «прибраться перед
закрытием». Для этого есть аннотации `@PostConstruct` и `@PreDestroy` из пакета `jakarta.annotation`.

```java
import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;

@Service
public class ConnectionPoolService {
    private final DataSourceProperties props;
    private Connection connection;

    public ConnectionPoolService(DataSourceProperties props) {
        this.props = props;   // ← зависимости уже внедрены, но ресурсы ещё не открыты
    }

    @PostConstruct   // ← вызовется ОДИН раз, когда бин полностью собран
    public void init() {
        this.connection = openConnection(props);   // ← безопасно: props уже на месте
        // здесь же удобно прогреть кэш, проверить миграции, залогировать старт
    }

    @PreDestroy   // ← вызовется при остановке контекста (graceful shutdown)
    public void cleanup() {
        if (connection != null) {
            connection.close();   // ← освобождаем ресурс, чтобы не утекло
        }
    }
}
```

⚠️ Важный момент: не открывайте ресурсы прямо в конструкторе. На этапе конструктора часть зависимостей или
настроек может быть ещё не готова, а исключение в конструкторе уронит создание бина. `@PostConstruct`
гарантирует, что *все* зависимости уже внедрены.

✅ `@PostConstruct` — прогрев кэша, валидация конфигурации, открытие соединений.
✅ `@PreDestroy` — закрытие пулов, флаш буферов, отписка от очередей.

## Ленивая инициализация: @Lazy

По умолчанию Spring создаёт все singleton-бины **сразу при старте контекста** (eager). Это хорошо: ошибки
конфигурации всплывают на старте, а не в проде под нагрузкой. Но иногда бин тяжёлый и нужен редко — тогда
его создание можно отложить до первого обращения.

```java
@Service
@Lazy   // ← бин будет создан НЕ на старте, а при первом фактическом использовании
public class ReportGenerator {

    public ReportGenerator() {
        // допустим, тут дорогая инициализация — грузим тяжёлые шаблоны
    }
}
```

`@Lazy` можно повесить и на точку инъекции, отложив создание зависимости:

```java
@Service
public class DashboardService {
    private final ReportGenerator generator;

    public DashboardService(@Lazy ReportGenerator generator) {   // ← прокси, реальный бин создастся при вызове
        this.generator = generator;
    }
}
```

⚠️ Не злоупотребляйте `@Lazy`. Отложенное создание прячет ошибки конфигурации: бин с опечаткой в зависимости
не упадёт на старте, а взорвётся позже — в самый неподходящий момент. Используйте `@Lazy` точечно, для
действительно тяжёлых и редко нужных бинов.

## Заключение

**Что изучено:**

- Бин — объект под управлением контейнера; объект из `new` бином не является.
- Объявить бин можно стереотипами (`@Component`/`@Service`/…) или фабричным `@Bean` в `@Configuration`.
- Жизненный цикл: instantiate → populate → *Aware → BPP.before → инициализация → BPP.after → работа → уничтожение.
- `@PostConstruct` / `@PreDestroy` (из `jakarta.annotation`) — точки для инициализации и освобождения ресурсов.
- По умолчанию бины создаются eager на старте; `@Lazy` откладывает создание до первого обращения.

**Как применять на практике:**

- Открывайте ресурсы в `@PostConstruct`, а не в конструкторе — там все зависимости гарантированно на месте.
- Освобождайте ресурсы в `@PreDestroy`, чтобы избежать утечек при остановке приложения.
- Для классов из библиотек используйте `@Bean`, для своих — стереотипы.
- `@Lazy` применяйте осознанно: он экономит старт, но прячет ошибки конфигурации.
