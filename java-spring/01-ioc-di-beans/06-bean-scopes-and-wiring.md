# Лекция: Scope бинов и выбор реализации

> Java Spring · Модуль 1 — IoC, DI и бины · [⬅ К содержанию трека](../README.md)

## Введение

Представьте офисное здание. Кофемашина в холле — одна на всех: любой сотрудник подходит к *тому же самому*
аппарату. А вот бейдж-пропуск — у каждого свой, личный, новый экземпляр на человека. Есть вещи общие, а
есть индивидуальные — и важно не перепутать, иначе либо очередь к единственному пропуску, либо сотня
ненужных кофемашин.

В Spring то же самое решает **scope бина**: сколько экземпляров бина создавать и как долго они живут. По
умолчанию бин — это «кофемашина на всех» (singleton), и здесь кроется ловушка с общим состоянием. А ещё
бывает, что под один интерфейс есть несколько реализаций, и контейнеру нужно подсказать, какую выбрать.
Давайте разберём и то, и другое — это завершит наш фундамент по DI.

## Что такое scope бина

**Scope** определяет жизненный цикл и количество экземпляров бина в контейнере. Основные scope-ы:

| Scope | Сколько экземпляров | Время жизни | Когда применять |
|---|---|---|---|
| `singleton` (по умолчанию) | один на контейнер | весь срок жизни контекста | большинство бинов: сервисы, репозитории |
| `prototype` | новый на каждый запрос бина | до тех пор, пока нужен вызвавшему | бины с состоянием, нужен свежий экземпляр |
| `request` | один на HTTP-запрос | в пределах запроса | веб-данные, привязанные к запросу |
| `session` | один на HTTP-сессию | пока живёт сессия | данные пользователя в сессии |

`singleton` и `prototype` доступны всегда; `request` и `session` — только в веб-приложении.

```java
@Service
@Scope("prototype")   // ← на каждый запрос этого бина контейнер отдаст НОВЫЙ экземпляр
public class ReportBuilder {
    private final List<String> rows = new ArrayList<>();   // ← у каждого свой набор строк

    public void addRow(String row) { rows.add(row); }
}
```

## Почему singleton по умолчанию и чем он опасен

Singleton — разумный дефолт: сервисы и репозитории обычно **stateless** (без изменяемого состояния), и
держать по одному экземпляру экономит память и время на создание. Один объект обслуживает все запросы — и
это нормально, пока он не хранит изменяемые данные.

⚠️ Опасность singleton — **общее изменяемое состояние**. Singleton-бин один на всё приложение, и к нему
одновременно обращается множество потоков. Изменяемое поле превращается в гонку данных.

```java
// ❌ ОПАСНО: singleton с изменяемым полем — поле общее для всех потоков
@Service
public class CounterService {
    private int lastCount;   // ← общее состояние! параллельные запросы будут затирать друг друга

    public int process(Request req) {
        this.lastCount = req.size();   // ← поток A пишет, поток B читает чужое значение
        return this.lastCount;
    }
}
```

```java
// ✅ БЕЗОПАСНО: singleton без изменяемого состояния — данные живут в локальных переменных
@Service
public class CounterService {

    public int process(Request req) {
        int count = req.size();   // ← локальная переменная, у каждого вызова своя
        return count;
    }
}
```

Правило: **singleton-бины делайте stateless.** Изменяемые данные держите в локальных переменных метода или
в специально предназначенных для состояния бинах с подходящим scope. `final`-зависимости, внедрённые через
конструктор, безопасны — их не меняют после старта.

## Несколько реализаций интерфейса

Часто под один интерфейс есть несколько реализаций. Тогда контейнер растеряется: какую внедрять? Spring
даёт несколько инструментов.

Допустим, есть интерфейс уведомлений и две реализации:

```java
public interface NotificationSender {
    void send(String to, String message);
}

@Service
public class EmailSender implements NotificationSender { /* ... */ }

@Service
public class SmsSender implements NotificationSender { /* ... */ }
```

Если просто попросить `NotificationSender`, Spring упадёт с ошибкой `NoUniqueBeanDefinitionException` —
кандидатов двое. Разрешаем неоднозначность.

**Вариант 1 — `@Primary`: пометить реализацию «по умолчанию».**

```java
@Service
@Primary   // ← если явно не указано иное, внедрять именно этот бин
public class EmailSender implements NotificationSender { /* ... */ }
```

**Вариант 2 — `@Qualifier`: выбрать конкретный бин по имени в точке инъекции.**

```java
@Service
public class AlertService {
    private final NotificationSender sender;

    public AlertService(@Qualifier("smsSender") NotificationSender sender) {   // ← именно SMS, по имени бина
        this.sender = sender;
    }
}
```

**Вариант 3 — внедрить *все* реализации сразу: `List<T>` или `Map<String, T>`.**

```java
@Service
public class BroadcastService {
    private final List<NotificationSender> senders;   // ← Spring соберёт ВСЕ реализации в список

    public BroadcastService(List<NotificationSender> senders) {
        this.senders = senders;
    }

    public void broadcast(String to, String message) {
        senders.forEach(s -> s.send(to, message));   // ← разошлём по всем каналам сразу
    }
}
```

`Map<String, NotificationSender>` соберёт реализации с *именами бинов в качестве ключей* — удобно, когда
нужно выбрать канал динамически по строке (`senders.get("emailSender")`).

| Инструмент | Что делает | Когда использовать |
|---|---|---|
| `@Primary` | назначает реализацию по умолчанию | есть «основной» вариант, остальные — редкие |
| `@Qualifier` | выбирает бин по имени в точке инъекции | нужна конкретная реализация именно здесь |
| `List<T>` | внедряет все реализации списком | нужно обойти/применить все сразу |
| `Map<String, T>` | все реализации с ключами-именами | выбор канала динамически по строке |

## Условные бины: @Conditional и @ConditionalOnProperty

Иногда реализацию нужно выбирать не в коде, а по настройке окружения. `@ConditionalOnProperty` создаёт бин
только при определённом значении свойства — это основа гибкой конфигурации.

```java
@Service
@ConditionalOnProperty(name = "notifications.channel", havingValue = "sms")
public class SmsSender implements NotificationSender { /* ... */ }   // ← создастся только если notifications.channel=sms

@Service
@ConditionalOnProperty(
        name = "notifications.channel",
        havingValue = "email",
        matchIfMissing = true)   // ← email по умолчанию, если свойство не задано вовсе
public class EmailSender implements NotificationSender { /* ... */ }
```

Теперь канал переключается одной строкой в `application.yml`:

```yaml
notifications:
  channel: sms   # ← поменяли значение — поменялась активная реализация, код трогать не нужно
```

`@ConditionalOnProperty` — частный случай более общего `@Conditional`, на котором, по сути, держится вся
автоконфигурация Spring Boot: бины подключаются в зависимости от того, что есть в classpath и какие свойства
заданы.

## Циклические зависимости и как их избегать

**Циклическая зависимость (circular dependency)** — это когда бин A зависит от B, а B — обратно от A.

```
   ┌─────────┐  нужен B   ┌─────────┐
   │    A    │ ─────────▶ │    B    │
   │         │ ◀───────── │         │
   └─────────┘  нужен A   └─────────┘
        ▲                      │
        └──────── тупик ───────┘
```

```java
// ❌ цикл через конструкторы — контейнер не сможет создать ни одного из них
@Service
public class A {
    public A(B b) { /* ... */ }   // ← для создания A нужен готовый B...
}

@Service
public class B {
    public B(A a) { /* ... */ }   // ← ...а для B нужен готовый A. Тупик!
}
```

При конструкторной инъекции Spring обнаружит цикл и **упадёт на старте** с понятной ошибкой — и это хорошо:
проблему видно сразу, а не в проде.

⚠️ Важно понимать: цикл — это почти всегда сигнал о *проблеме дизайна*, а не задача, которую надо «обойти»
костылём. Как разорвать:

- **Выделить третий компонент.** Часто общую логику A и B стоит вынести в новый сервис C, от которого зависят
  оба, — цикл исчезает.
- **Пересмотреть ответственности.** Возможно, обязанности размазаны между A и B и их стоит перераспределить.
- `@Lazy` на одной из зависимостей формально разрывает цикл (внедряется прокси), но это лишь маскировка —
  лечите причину, а не симптом.

✅ Лучшая профилактика — конструкторная инъекция: она *не даёт* циклу проскользнуть незаметно, заставляя
исправить дизайн сразу.

## Заключение

**Что изучено:**

- Scope задаёт число экземпляров и время жизни бина: `singleton` (по умолчанию), `prototype`, `request`, `session`.
- Singleton опасен общим изменяемым состоянием — такие бины держите stateless.
- Несколько реализаций интерфейса разрешаются через `@Primary`, `@Qualifier` или инъекцию `List<T>`/`Map<String, T>`.
- `@ConditionalOnProperty` (частный случай `@Conditional`) выбирает бин по настройке — основа автоконфигурации.
- Циклические зависимости — признак проблемы дизайна; конструкторная инъекция ловит их на старте.

**Как применять на практике:**

- Оставляйте `singleton` по умолчанию и не храните в таких бинах изменяемое состояние.
- Для нескольких реализаций выбирайте: `@Primary` — основной вариант, `@Qualifier` — точечный выбор, `List`/`Map` — все сразу.
- Переключайте реализации через `@ConditionalOnProperty` и свойства, не меняя код.
- Увидев цикл — не глушите его `@Lazy`, а выносите общую логику в отдельный компонент.
