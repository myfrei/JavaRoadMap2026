# Лекция: Инверсия управления и внедрение зависимостей

> Java Spring · Модуль 1 — IoC, DI и бины · [⬅ К содержанию трека](../README.md)

## Введение

Представьте, что вы готовите ужин и каждый раз сами выращиваете картошку, держите корову ради молока и
строите печь с нуля. Звучит абсурдно — обычно вы просто берёте готовые продукты из холодильника и
пользуетесь плитой, которую кто-то уже установил. Вам важен результат — блюдо, а не происхождение каждой
морковки.

В коде та же история. Когда класс сам создаёт всё, что ему нужно (через `new`), он жёстко привязывается к
конкретным реализациям — словно повар, который не может приготовить суп без своей единственной грядки.
Давайте разберём, как Spring переворачивает эту логику: класс просто говорит «мне нужен репозиторий», а
кто и как его создаст — забота контейнера. Этот разворот ответственности и называется **Inversion of
Control (IoC)**, а конкретный приём передачи готовых зависимостей — **Dependency Injection (DI)**.

## Проблема: жёсткая связанность

Вы наверняка писали код, где один класс внутри себя создаёт другой. Посмотрим, чем это плохо.

```java
// ❌ сервис сам создаёт зависимость через new
public class OrderService {
    private final OrderRepository repo = new JdbcOrderRepository();  // ← жёстко прибито гвоздями

    public void placeOrder(Order order) {
        repo.save(order);
    }
}
```

Что здесь не так:

- **Не подменить реализацию.** Захотели перейти с JDBC на in-memory для прототипа — придётся лезть внутрь
  класса и править код.
- **Не протестировать.** В unit-тесте нельзя передать «фейковый» репозиторий — `OrderService` намертво
  связан с `JdbcOrderRepository`, который полезет в настоящую базу.
- **Скрытая зависимость.** Глядя на конструктор, не видно, от чего класс реально зависит — всё спрятано
  внутри тела.

Класс знает слишком много: и *что* ему нужно, и *как* это создать. Эти две заботы стоит разделить.

## Что такое IoC: принцип Голливуда

**Inversion of Control** — это принцип, при котором управление потоком и созданием объектов передаётся
внешней силе (фреймворку, контейнеру), а не зашито в вашем коде. Его часто описывают **«принципом
Голливуда»**: *«Don't call us — we'll call you»* («не звоните нам — мы позвоним вам»).

Без IoC ваш код сам всё дёргает: создаёт объекты, решает, когда их вызвать. С IoC всё наоборот — вы
описываете компоненты, а контейнер сам решает, когда их создать и кому передать.

```
Классический подход                       Inversion of Control
┌──────────────────┐                      ┌──────────────────┐
│  Ваш код         │                      │  Контейнер       │
│  new Repo()      │ ── управляет ──▶     │  создаёт объекты │
│  new Service()   │      объектами       │  и связывает их  │
└──────────────────┘                      └────────┬─────────┘
                                                    │ внедряет
                                                    ▼
                                          ┌──────────────────┐
                                          │  Ваши классы     │
                                          │  (просто логика) │
                                          └──────────────────┘
```

IoC — это широкий принцип. DI — самый популярный способ его реализовать.

## DI как реализация IoC

**Dependency Injection** — это передача классу его зависимостей *извне*, вместо того чтобы он создавал
их сам. «Внедрить зависимость» = «дать объекту готовый объект, который ему нужен».

```java
@Service
public class OrderService {
    private final OrderRepository repo;   // ← зависимость, но НЕ создаём её здесь

    public OrderService(OrderRepository repo) {   // ← она ПРИХОДИТ извне, через конструктор
        this.repo = repo;
    }

    public void placeOrder(Order order) {
        repo.save(order);
    }
}
```

Теперь `OrderService` не знает, *какой именно* репозиторий ему дадут — JDBC, in-memory или мок. Он
работает с интерфейсом `OrderRepository`. Это и есть слабая связанность (loose coupling): компоненты
зависят от абстракций, а не от конкретных классов.

## Три вида инъекции

Spring умеет внедрять зависимости тремя способами. Разберём каждый.

**1. Конструкторная инъекция (constructor injection)** — зависимости приходят как параметры конструктора.

```java
@Service
public class OrderService {
    private final OrderRepository repo;     // ← можно сделать final

    public OrderService(OrderRepository repo) {   // ← Spring вызовет этот конструктор
        this.repo = repo;
    }
}
```

**2. Сеттерная инъекция (setter injection)** — через сеттер, помеченный `@Autowired`.

```java
@Service
public class OrderService {
    private OrderRepository repo;   // ← не final, можно переприсвоить

    @Autowired
    public void setOrderRepository(OrderRepository repo) {
        this.repo = repo;
    }
}
```

**3. Полевая инъекция (field injection)** — прямо в поле, через `@Autowired`.

```java
@Service
public class OrderService {
    @Autowired
    private OrderRepository repo;   // ❌ удобно, но проблемно (см. ниже)
}
```

### Почему конструкторная предпочтительна

| Критерий | Конструктор | Сеттер | Поле |
|---|---|---|---|
| `final`-поля (неизменяемость) | ✅ да | ❌ нет | ❌ нет |
| Объект всегда валиден после создания | ✅ да | ❌ может быть `null` | ❌ может быть `null` |
| Зависимости видны явно | ✅ в сигнатуре | ⚠️ частично | ❌ спрятаны |
| Тест без Spring (`new Service(mock)`) | ✅ легко | ⚠️ через сеттер | ❌ нужен reflection |
| Видно «разбухание» класса (много зависимостей) | ✅ длинный конструктор кричит | ❌ незаметно | ❌ незаметно |
| Циклические зависимости | ✅ ловятся на старте | ⚠️ маскируются | ⚠️ маскируются |

Конструкторная инъекция — официально рекомендуемый Spring-командой стиль. Поля `final`, объект сразу
готов к работе, зависимости честно перечислены, а в тесте достаточно `new OrderService(mockRepo)` без
поднятия контекста. Полевую инъекцию избегайте: она прячет зависимости и мешает тестам.

## IoC-контейнер и ApplicationContext

Кто же создаёт объекты и внедряет их? Это делает **IoC-контейнер** Spring. Его центральный интерфейс —
`ApplicationContext`: реестр всех управляемых объектов (бинов), который умеет их создавать, связывать и
выдавать по запросу.

```java
@SpringBootApplication
public class App {
    public static void main(String[] args) {
        // run(...) поднимает ApplicationContext — контейнер сканирует классы,
        // создаёт бины и внедряет зависимости
        ApplicationContext ctx = SpringApplication.run(App.class, args);   // ← контейнер готов

        OrderService service = ctx.getBean(OrderService.class);   // ← забираем готовый бин
        // service уже получил свой OrderRepository — нам не пришлось вызывать new
    }
}
```

На практике вы почти никогда не дёргаете `getBean` вручную — Spring сам раздаёт зависимости туда, где они
нужны. Но важно понимать: за кулисами есть контейнер, который держит граф объектов.

## @Autowired и почему на конструкторе он не нужен

Аннотация `@Autowired` помечает точку, куда Spring должен подставить зависимость. На сеттере и поле она
обязательна. А вот на конструкторе — нет.

```java
@Service
public class OrderService {
    private final OrderRepository repo;

    // @Autowired здесь НЕ нужен ←
    public OrderService(OrderRepository repo) {   // единственный конструктор → Spring и так его вызовет
        this.repo = repo;
    }
}
```

⚠️ Правило: если в классе **ровно один конструктор**, Spring использует его автоматически — `@Autowired`
писать не нужно (это поведение начиная со Spring 4.3). Аннотация нужна, только когда конструкторов
несколько и надо указать, какой из них предпочесть.

## Складываем вместе: сервис → репозиторий

Соберём минимальный, но рабочий пример связки «сервис зависит от репозитория».

```java
// Интерфейс — абстракция, от которой зависит сервис
public interface OrderRepository {
    void save(Order order);
}

// Конкретная реализация — Spring сделает её бином благодаря @Repository
@Repository
public class JdbcOrderRepository implements OrderRepository {
    @Override
    public void save(Order order) {
        // ... сохранение в БД
    }
}

// Сервис получает репозиторий через конструктор — не знает, какая реализация придёт
@Service
public class OrderService {
    private final OrderRepository repo;   // ← зависим от интерфейса, не от класса

    public OrderService(OrderRepository repo) {
        this.repo = repo;
    }

    public void placeOrder(Order order) {
        repo.save(order);   // ← вызываем через абстракцию
    }
}
```

Что произошло: Spring увидел `@Repository` и `@Service`, создал оба бина, обнаружил, что `OrderService`
просит `OrderRepository`, нашёл единственную подходящую реализацию (`JdbcOrderRepository`) и передал её в
конструктор. Вы не написали ни одного `new` — контейнер собрал граф объектов за вас.

В тесте это раскрывается во всей красе:

```java
@Test
void placesOrder() {
    OrderRepository fake = order -> { /* ничего не делаем */ };   // ← подменяем мок
    OrderService service = new OrderService(fake);   // ← без Spring, мгновенно

    service.placeOrder(new Order());   // ← проверяем логику в изоляции
}
```

## Заключение

**Что изучено:**

- Жёсткая связанность (`new` внутри класса) мешает подменять реализации и тестировать код.
- **IoC** — принцип «не звоните нам — мы позвоним вам»: созданием объектов управляет контейнер, а не ваш код.
- **DI** — реализация IoC: зависимости приходят извне (конструктор / сеттер / поле).
- Конструкторная инъекция предпочтительна: `final`-поля, валидный объект, видимые зависимости, лёгкие тесты.
- Контейнер представлен интерфейсом `ApplicationContext`; `@Autowired` на единственном конструкторе не нужен.

**Как применять на практике:**

- Зависьте от интерфейсов, а не от конкретных классов.
- Внедряйте зависимости через конструктор и храните их в `final`-полях.
- Не пишите `@Autowired` на единственном конструкторе — Spring справится сам.
- Длинный список параметров конструктора — сигнал, что класс делает слишком много; подумайте о разбиении.
