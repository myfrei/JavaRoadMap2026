# Лекция: Сервисный слой и аннотация @Service

> Java Spring · Модуль 1 — IoC, DI и бины · [⬅ К содержанию трека](../README.md)

## Введение

Представьте ресторан. Официант (веб-слой) принимает заказ и приносит блюдо, но *готовит* не он — готовит
кухня. Кладовщик (слой данных) выдаёт продукты, но не решает, что из них приготовить. А вот шеф-повар —
это сердце процесса: он знает рецепты, комбинирует ингредиенты, следит за качеством. Уберите шефа — и
официант с кладовщиком просто перекладывают вещи, не понимая, что должно получиться.

В приложении роль шеф-повара играет **сервисный слой (service layer)**: здесь живёт бизнес-логика —
правила, расчёты, сценарии. Вы наверняка видели соблазн «просто дописать пару строк в контроллер» — давайте
разберём, почему логике место именно в сервисах, и как это упрощает тесты и развитие проекта.

## Что такое сервисный слой и зачем он нужен

Типичный бэкенд делят на три слоя:

```
   ┌─────────────────┐     HTTP-запросы, валидация формата,
   │   Controller    │ ←── маппинг JSON. НЕ бизнес-логика.
   └────────┬────────┘
            │ вызывает
            ▼
   ┌─────────────────┐     БИЗНЕС-ЛОГИКА: правила, расчёты,
   │    Service       │ ←── сценарии, транзакции, оркестрация.
   └────────┬────────┘
            │ вызывает
            ▼
   ┌─────────────────┐     доступ к данным: SQL, запросы,
   │   Repository    │ ←── маппинг строк в объекты. НЕ логика.
   └─────────────────┘
```

Сервисный слой — это «прослойка» между вебом и данными, где сосредоточены *решения*: можно ли оформить
заказ, какую скидку применить, что произойдёт при отмене. Он не знает про HTTP (не его забота) и не пишет
SQL руками (это к репозиторию) — он *оркестрирует*.

Зачем выделять его отдельно:

- **Переиспользование.** Одну и ту же логику могут вызвать и REST-контроллер, и фоновая задача, и
  обработчик сообщения из очереди.
- **Тестируемость.** Чистую логику легко проверить unit-тестами без HTTP и базы.
- **Ясность.** Контроллеры остаются тонкими, репозитории — простыми, а сложность собрана в одном месте.

## @Service vs @Component: семантика стереотипов

Технически `@Service` — это `@Component` с другим именем: оба делают класс бином. Но стереотипы несут
**семантику** — сообщают читателю и инструментам *роль* класса.

```java
@Service   // ← «здесь бизнес-логика» — понятно с первого взгляда
public class OrderService { /* ... */ }
```

Семейство стереотипов:

| Аннотация | Слой | Смысл | Доп. поведение |
|---|---|---|---|
| `@Component` | любой | общий бин | — |
| `@Service` | бизнес-логика | сервис, сценарии | семантический маркер |
| `@Repository` | данные | доступ к БД | трансляция исключений БД в `DataAccessException` |
| `@Controller` | веб (MVC) | возвращает view | обрабатывается DispatcherServlet |
| `@RestController` | веб (API) | возвращает тело ответа | `@Controller` + `@ResponseBody` |

✅ Используйте `@Service` для классов с логикой, даже если функционально `@Component` сработал бы так же —
имя аннотации документирует архитектуру. `@Repository` вдобавок даёт реальную пользу: переводит низкоуровневые
исключения драйвера в единую иерархию Spring.

## Где живёт бизнес-логика: пример

Соберём сервис, который оформляет заказ. Обратите внимание: он только координирует — детали хранения у
репозитория, отправка письма у другого сервиса.

```java
@Service
public class OrderService {
    private final OrderRepository orderRepository;
    private final NotificationService notificationService;

    public OrderService(OrderRepository orderRepository,
                        NotificationService notificationService) {   // ← зависимости через конструктор
        this.orderRepository = orderRepository;
        this.notificationService = notificationService;
    }

    public Order placeOrder(Long customerId, List<Item> items) {
        if (items.isEmpty()) {                                  // ← бизнес-правило
            throw new EmptyOrderException("Заказ не может быть пустым");
        }
        BigDecimal total = calculateTotal(items);               // ← расчёт — это логика
        Order order = new Order(customerId, items, total);

        Order saved = orderRepository.save(order);              // ← хранение делегируем репозиторию
        notificationService.notifyOrderPlaced(saved);           // ← побочный эффект — другому сервису
        return saved;
    }

    private BigDecimal calculateTotal(List<Item> items) {
        return items.stream()
                .map(Item::price)
                .reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}
```

Сервис читается как описание сценария: проверь → посчитай → сохрани → уведоми. Никакого HTTP, никакого SQL —
только суть.

## @Transactional: атомарность операций (кратко)

Бизнес-операция часто состоит из нескольких шагов с базой, и они должны выполниться «всё или ничего».
Аннотация `@Transactional` оборачивает метод в транзакцию: упало в середине — откатятся все изменения.

```java
@Service
public class OrderService {

    @Transactional   // ← весь метод в одной транзакции: ошибка → откат всех изменений в БД
    public Order placeOrder(Long customerId, List<Item> items) {
        Order order = orderRepository.save(buildOrder(customerId, items));
        inventoryRepository.decreaseStock(items);   // ← если упадёт здесь, save выше откатится
        return order;
    }
}
```

Здесь важно понять *где* живёт `@Transactional` — на сервисном слое, потому что именно он определяет
границы бизнес-операции. Механику (распространение, уровни изоляции, откаты) подробно разберём в **Модуле 2**
при работе с базой данных — пока достаточно знать, что транзакциями управляет сервис.

## Тестируемость: мок репозитория без Spring

Главный практический бонус выделенного сервиса — его можно проверить *в изоляции*, не поднимая Spring и не
подключая базу. Зависимости приходят через конструктор, значит, в тесте мы передаём моки.

```java
@Test
void rejectsEmptyOrder() {
    OrderRepository repo = mock(OrderRepository.class);              // ← мок репозитория
    NotificationService notifier = mock(NotificationService.class); // ← мок уведомлений
    OrderService service = new OrderService(repo, notifier);        // ← обычный new, без контекста

    assertThrows(EmptyOrderException.class,
            () -> service.placeOrder(1L, List.of()));               // ← проверяем бизнес-правило

    verifyNoInteractions(repo);   // ← убедились: в пустом заказе до базы дело не дошло
}
```

Тест запускается за миллисекунды и проверяет именно логику. Так и работает связка «DI + сервисный слой»:
зависимости снаружи → лёгкая подмена → быстрые надёжные тесты.

## Анти-паттерн: жирный контроллер

А теперь — как делать **не надо**. Соблазн положить логику прямо в контроллер встречается постоянно.

```java
// ❌ «жирный контроллер»: бизнес-логика, расчёты и работа с БД смешаны с веб-слоем
@RestController
public class OrderController {
    private final OrderRepository orderRepository;

    @PostMapping("/orders")
    public Order create(@RequestBody OrderRequest req) {
        if (req.items().isEmpty()) { /* ... */ }                    // ← логика в контроллере
        BigDecimal total = req.items().stream()                     // ← расчёт в контроллере
                .map(Item::price).reduce(BigDecimal.ZERO, BigDecimal::add);
        Order order = new Order(req.customerId(), req.items(), total);
        return orderRepository.save(order);                         // ← прямой доступ к БД из веба
        // а отправку письма? а транзакцию? всё сюда же — и метод разрастается
    }
}
```

Чем это плохо:

- Логику **нельзя переиспользовать** — она заперта внутри HTTP-обработчика.
- Тест требует **поднимать веб-слой**, хотя проверяем-то правила, а не маршрутизацию.
- Контроллер пухнет, смешивая три ответственности; читать и менять его всё труднее.

✅ Правильно: контроллер принимает запрос и делегирует сервису. Один-два вызова — и всё.

```java
@RestController
public class OrderController {
    private final OrderService orderService;   // ← зависим от сервиса, а не от репозитория

    @PostMapping("/orders")
    public Order create(@RequestBody OrderRequest req) {
        return orderService.placeOrder(req.customerId(), req.items());   // ← вся логика — там
    }
}
```

## Заключение

**Что изучено:**

- Сервисный слой — место бизнес-логики между веб-слоем и слоем данных; он оркестрирует, а не лезет в HTTP/SQL.
- `@Service` = `@Component` по механике, но несёт семантику роли; `@Repository` ещё и транслирует исключения БД.
- `@Transactional` задаёт границы бизнес-операции и живёт на сервисе (детали — в Модуле 2).
- Зависимости через конструктор делают сервис тестируемым: моки вместо реальных репозиториев, без Spring.
- «Жирный контроллер» — анти-паттерн: логику в контроллере нельзя переиспользовать и тяжело тестировать.

**Как применять на практике:**

- Держите контроллеры тонкими: приняли запрос — делегировали сервису.
- Всю логику и расчёты выносите в `@Service`; репозиторий пусть только читает/пишет данные.
- Пишите unit-тесты сервисов с моками зависимостей — быстро и без инфраструктуры.
- Границы транзакций ставьте на методах сервиса, а не контроллера или репозитория.

**Что дальше:** поднимемся на веб-слой и разберём контроллеры — `@Controller` и `@RestController`.
