# Пул соединений (HikariCP)

> Модуль 5 — Базы данных · [к модулю](../../../course/05-databases.md)

## Зачем это нужно

Открытие соединения с БД — дорогая операция: TCP-handshake, аутентификация, выделение ресурсов на
сервере (десятки миллисекунд). Если открывать соединение на каждый запрос, БД ляжет под нагрузкой.
**Пул соединений** держит набор уже открытых соединений и выдаёт их по требованию — это обязательная
часть любого сервиса, работающего с БД.

**Где применяется в проектах:** каждый бэкенд с БД; Spring Boot по умолчанию использует HikariCP;
настройка размера пула — частая задача при тюнинге производительности.

## Без пула — медленно

```java
// ❌ на каждый запрос новое соединение — дорого и не масштабируется
try (Connection c = DriverManager.getConnection(url, user, password);
     var ps = c.prepareStatement("SELECT 1")) {
    ps.executeQuery();
}   // соединение закрывается и теряется
```

## С пулом — соединение переиспользуется

```java
HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:postgresql://localhost:5432/appdb");
config.setUsername("app");
config.setPassword("secret");
config.setMaximumPoolSize(10);          // не больше 10 соединений к БД одновременно
config.setConnectionTimeout(2_000);     // ждать свободное не дольше 2 сек

try (HikariDataSource pool = new HikariDataSource(config)) {
    try (Connection c = pool.getConnection();          // берём из пула (не открываем заново)
         var ps = c.prepareStatement("SELECT 1")) {
        ps.executeQuery();
    }   // c.close() ВОЗВРАЩАЕТ соединение в пул, а не закрывает физически
}
```

Главное переосмысление: `connection.close()` при работе с пулом **не закрывает** соединение —
оно возвращается в пул для переиспользования. Поэтому всегда оборачивай в try-with-resources.

## Размер пула: меньше, чем кажется

Интуиция «больше соединений = быстрее» неверна. БД эффективно обслуживает ограниченное число
параллельных запросов. Типичная отправная точка: `pool size ≈ количество ядер БД × 2`.
Слишком большой пул создаёт конкуренцию и деградацию.

## Утечки соединений

Если забыть закрыть соединение, оно не вернётся в пул — пул исчерпается, и сервис «зависнет» на
`getConnection`. HikariCP умеет это ловить:

```java
config.setLeakDetectionThreshold(5_000);  // лог, если соединение держат > 5 сек
```

## Связь с кодом модуля

Репозитории модуля (`InMemoryRepository` в
[homework](../homework/src/main/java/com/javaroadmap/m05/homework/Mod05Homework.java)) в реальной
версии берут `Connection` из пула на каждый метод и сразу возвращают его. Пул — невидимый, но
критичный слой под любым DAO.

## Итог

**Что изучено:**
- Открытие соединения дорогое — его переиспользуют через пул.
- HikariCP: `getConnection` берёт из пула, `close` возвращает обратно.
- Размер пула небольшой и подбирается под БД; утечки ловятся `leakDetectionThreshold`.

**Как применять на практике:**
- Никогда не открывать соединения напрямую в проде — только через пул (HikariCP по умолчанию в Spring Boot).
- Всегда закрывать `Connection`/`Statement`/`ResultSet` через try-with-resources.
- Настраивать размер пула по нагрузке и возможностям БД, а не «побольше».
