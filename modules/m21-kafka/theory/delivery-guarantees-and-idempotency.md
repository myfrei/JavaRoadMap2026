# Гарантии доставки и идемпотентность

> Модуль 21 — Kafka · [к модулю](../../../course/21-kafka.md)

## Зачем это нужно

В распределённых системах сообщения теряются, дублируются и приходят не по порядку. Если обработчик
не готов к повторной доставке, один платёж спишется дважды. Идемпотентность и правильный коммит
оффсетов — это то, что превращает «иногда работает» в «надёжно».

**Где применяется в проектах:** обработка платежей и заказов; интеграции между сервисами; любые
консьюмеры Kafka/RabbitMQ; вебхуки (их тоже шлют повторно).

## Три гарантии доставки

| Гарантия | Что значит | Цена |
|----------|-----------|------|
| at-most-once | максимум один раз, можно потерять | просто, но теряет данные |
| **at-least-once** | хотя бы один раз, возможны дубли | стандарт; требует идемпотентности |
| exactly-once | ровно один раз | дорого, ограниченно (Kafka transactions) |

На практике берут **at-least-once + идемпотентную обработку** — это даёт эффект «ровно один раз»
по результату.

## Оффсеты: коммить ПОСЛЕ обработки

Оффсет — позиция консьюмера в партиции. Если закоммитить оффсет *до* обработки и упасть — сообщение
потеряется (at-most-once). Поэтому коммитят **после** успешной обработки:

```java
records.forEach(this::process);   // 1) сначала обработали
consumer.commitSync();            // 2) потом закоммитили оффсет
// если упали между 1 и 2 — после рестарта обработаем повторно (at-least-once)
```

Отсюда вытекает: повтор возможен, значит обработка обязана быть идемпотентной.

## Идемпотентность: дубликат не меняет результат

Идемпотентная операция при повторе даёт тот же эффект. Простейший приём — дедупликация по уникальному
id сообщения:

```java
class IdempotentProcessor {
    private final Set<String> seen = new HashSet<>();   // в проде — Redis/таблица с UNIQUE

    boolean process(String messageId) {
        if (!seen.add(messageId)) {   // add вернёт false, если id уже был
            return false;             // дубликат — пропускаем, эффект не повторяем
        }
        // ... выполнить бизнес-логику ровно один раз ...
        return true;
    }
}
```

`seen.add(id)` атомарно проверяет-и-вставляет: если id уже есть — это повтор. В реальной системе
вместо `HashSet` — таблица с UNIQUE-ограничением или Redis с TTL.

## Безопасный оффсет при параллельной обработке

Если сообщения обрабатываются не строго по порядку, коммитить можно только **непрерывный префикс**
обработанного: коммит = первый «разрыв».

```text
обработаны {0,1,2,4}  ->  коммитим 3 (нельзя коммитить 5: тогда «потеряем» 3 при рестарте)
```

## Итог

**Что изучено:**
- Три гарантии доставки; на практике — at-least-once + идемпотентность ≈ exactly-once по результату.
- Коммитить оффсет ПОСЛЕ обработки; повтор неизбежен — готовься к нему.
- Дедупликация по уникальному id; коммит только непрерывного префикса.

**Как применять на практике:**
- Делать обработчики идемпотентными (UNIQUE-ключ в БД, Redis с TTL).
- Не коммитить оффсет/не подтверждать сообщение до завершения обработки.
- Гарантировать порядок по ключу через партиционирование, а не глобально.
