# Надёжность: партиции, retry, DLQ и компакция

> Модуль 21 — Kafka · [к модулю](../../../course/21-kafka.md)

## Зачем это нужно

Идемпотентности мало — нужно ещё решить, что делать с «ядовитыми» сообщениями (которые не
обрабатываются никогда), как сохранить порядок и как не дать одному сбою заблокировать всю очередь.
Эти приёмы отличают учебный консьюмер от боевого.

**Где применяется в проектах:** любые очереди под нагрузкой; интеграции, где часть сообщений
заведомо битая; системы, где важен порядок событий по сущности.

## Партиции = порядок + параллелизм

Топик разбит на партиции. Порядок гарантируется **внутри партиции**, а сообщения с одним ключом
всегда попадают в одну партицию:

```java
int partitionFor(String key, int partitions) {
    return Math.floorMod(key.hashCode(), partitions);  // один ключ -> одна партиция -> порядок
}
```

Поэтому ключ выбирают так, чтобы связанные события (например, по `orderId`) шли по порядку,
а разные заказы — параллельно по разным партициям.

## Retry с backoff

Временный сбой (сеть, недоступность БД) лечится повтором с нарастающей паузой, чтобы не долбить
упавший сервис:

```java
long backoff = baseMs * (1L << attempt);   // 100, 200, 400, 800... (экспонента)
```

## DLQ — карантин для «ядовитых» сообщений

Если сообщение не обрабатывается после N попыток, его нельзя повторять вечно — оно заблокирует
партицию. Его отправляют в **dead-letter-топик** и едут дальше:

```java
String route(int attempt, int maxRetries) {
    return attempt < maxRetries ? "RETRY" : "DLQ";   // исчерпали попытки -> в карантин
}
```

DLQ потом разбирают вручную или отдельным процессом. Главное — основной поток не стоит.

## Компакция лога (log compaction)

Для топиков «последнее состояние по ключу» Kafka умеет хранить только **последнее** значение каждого
ключа, удаляя старые. Логика «последний выигрывает по offset»:

```java
Map<String, String> latestByKey(List<KafkaRecord> records) {
    Map<String, String> last = new HashMap<>();
    for (KafkaRecord r : records) {
        last.put(r.key(), r.value());   // более поздний offset перезапишет ранний
    }
    return last;
}
```

Это даёт «таблицу из лога»: по каждому ключу — актуальное значение.

## Outbox: надёжная публикация из транзакции

Чтобы не было «записал в БД, но не отправил в Kafka» (или наоборот), событие пишут в таблицу
`outbox` **в той же транзакции**, что и бизнес-данные, а отдельный процесс публикует его в Kafka.
Так публикация согласована с изменением данных.

## Итог

**Что изучено:**
- Партиции дают порядок по ключу и параллелизм между ключами.
- Retry с экспоненциальным backoff; DLQ для «ядовитых» сообщений, чтобы не блокировать поток.
- Компакция «последний по ключу»; outbox для согласованной публикации.

**Как применять на практике:**
- Выбирать ключ партиционирования по сущности, для которой важен порядок.
- Ставить лимит ретраев и DLQ — никогда не повторять бесконечно.
- Публиковать события через outbox, когда важна согласованность с БД.
