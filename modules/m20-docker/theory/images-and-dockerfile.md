# Образы, слои и Dockerfile (multi-stage для JVM)

> Модуль 20 — Docker · [к модулю](../../../course/20-docker.md)

## Зачем это нужно

Контейнер упаковывает приложение вместе с окружением — «работает у меня» превращается в «работает
везде одинаково». Для JVM правильный `Dockerfile` решает две задачи: маленький и безопасный образ
(только JRE, не JDK и не исходники) и быстрые пересборки за счёт кэша слоёв.

**Где применяется в проектах:** доставка сервисов в любой среде; CI/CD; Kubernetes; локальное
поднятие зависимостей (БД, брокеры) одной командой.

## Образ = слои

Каждая инструкция `Dockerfile` создаёт **слой**. Слои кэшируются: если инструкция и её входные
данные не изменились, Docker переиспользует кэш. Поэтому порядок инструкций влияет на скорость
пересборки — редко меняющееся кладут выше.

## Multi-stage: собираем в одном образе, запускаем в другом

```dockerfile
# ── Стадия 1: сборка (нужен JDK + Gradle) ──
FROM eclipse-temurin:25-jdk AS build
WORKDIR /src
COPY gradlew settings.gradle.kts build.gradle.kts ./
COPY gradle ./gradle
COPY modules ./modules
RUN ./gradlew :modules:m20-docker:installDist --no-daemon

# ── Стадия 2: runtime (только JRE + собранный дистрибутив) ──
FROM eclipse-temurin:25-jre AS runtime
WORKDIR /app
RUN useradd --uid 1000 --create-home appuser
COPY --from=build /src/modules/m20-docker/build/install/m20-docker/ ./
USER appuser
EXPOSE 8080
ENTRYPOINT ["bin/m20-docker"]
```

Что здесь важно:
- **Две стадии**: тяжёлый JDK и исходники остаются в стадии `build` и НЕ попадают в финальный образ —
  он содержит только JRE и готовый дистрибутив. Образ меньше и безопаснее.
- `COPY --from=build` переносит из стадии сборки только нужные артефакты.
- `USER appuser` — запуск не от root (безопасность).
- Полный файл: [`../docker/Dockerfile`](../docker/Dockerfile).

## Кэш слоёв: копируй зависимости раньше кода

В примере выше сначала копируются файлы сборки (`gradlew`, `gradle/`), потом — модули. Если поменялся
только код, слой со скачанными зависимостями переиспользуется из кэша. Обратный порядок ломал бы кэш
на каждое изменение кода.

## Хороший Dockerfile — чек-лист

- закреплённая версия базового образа (не `:latest`);
- non-root `USER`;
- `HEALTHCHECK` для реального сервиса;
- `.dockerignore`, чтобы не тащить `build/`, `.git/` в контекст.

## Итог

**Что изучено:**
- Образ состоит из кэшируемых слоёв; порядок инструкций влияет на скорость пересборки.
- Multi-stage оставляет в runtime только JRE + артефакт — меньше и безопаснее.
- Базовые правила безопасности: пин версии, non-root, healthcheck.

**Как применять на практике:**
- Писать multi-stage Dockerfile для любого JVM-сервиса.
- Копировать зависимости раньше кода, чтобы беречь кэш и ускорять CI.
- Прогонять образ через линтер/правила (как в домашке) перед мержем.
