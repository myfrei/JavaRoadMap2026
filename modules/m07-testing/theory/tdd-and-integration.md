# TDD и интеграционные тесты (Testcontainers)

> Модуль 7 — Тестирование · [к модулю](../../../course/07-testing.md)

## Зачем это нужно

TDD (Test-Driven Development) — писать тест ДО кода — даёт чёткое определение «готово» и не даёт
писать лишнее. А интеграционные тесты проверяют, что компоненты работают вместе с **реальными**
зависимостями (настоящая БД, а не мок) — там, где юнит-тесты с моками лгут.

**Где применяется в проектах:** разработка «от теста» сложной логики; проверка SQL и миграций на
реальной БД; контрактные тесты API.

## Цикл TDD: red → green → refactor

1. **Red** — написать падающий тест на следующее требование.
2. **Green** — минимальный код, чтобы тест прошёл.
3. **Refactor** — улучшить код, тесты остаются зелёными.

```java
// red: тест есть, кода нет — падает
@Test
void emptyStringIsZero() {
    assertEquals(0, StringCalculator.add(""));
}
// green: минимум, чтобы прошло
static int add(String s) {
    if (s.isEmpty()) return 0;
    // ... дальше следующий красный тест на "1", потом "1,2" ...
}
```

Именно так устроена домашка курса: тесты уже «красные», твоя задача — сделать их зелёными,
двигаясь маленькими шагами. Это TDD «наоборот» — тесты даны заранее.

## Пирамида тестов

- **много** быстрых юнит-тестов (логика в изоляции);
- **меньше** интеграционных (с БД/очередью);
- **совсем мало** медленных e2e (через весь стек).

Перевёрнутая пирамида (много медленных e2e, мало юнитов) — частая ошибка: сборка тормозит, причины
падений неочевидны.

## Интеграционный тест с Testcontainers

Testcontainers поднимает реальную БД в Docker на время теста — без моков и без «общей» тестовой БД:

```java
@Testcontainers
class OrderRepositoryIT {

    @Container
    static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:17");

    @Test
    void savesAndLoads() {
        var repo = new JdbcOrderRepository(db.getJdbcUrl(), db.getUsername(), db.getPassword());
        repo.save(new Order(1, "NEW"));
        assertEquals("NEW", repo.findById(1).orElseThrow().status());  // настоящий SQL к реальной БД
    }
}
```

Контейнер создаётся перед тестами и удаляется после — каждый прогон на чистой БД, как в проде.

## Итог

**Что изучено:**
- Цикл TDD red → green → refactor; маленькими шагами от теста к коду.
- Пирамида тестов: много юнитов, меньше интеграционных, мало e2e.
- Testcontainers поднимает реальную БД в Docker для честных интеграционных тестов.

**Как применять на практике:**
- Для сложной логики писать тест первым — это уточняет требования и страхует рефакторинг.
- Проверять SQL, миграции и репозитории на реальной БД (Testcontainers), а не на моках.
- Держать здоровую пирамиду: основная масса — быстрые юнит-тесты.
