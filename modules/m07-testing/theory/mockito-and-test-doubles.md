# Mockito и тестовые дублёры

> Модуль 7 — Тестирование · [к модулю](../../../course/07-testing.md)

## Зачем это нужно

Юнит-тест должен проверять **одну** единицу в изоляции. Но реальные классы зависят от БД, HTTP,
очередей — медленных и недетерминированных. Тестовые дублёры (моки, стабы) подменяют эти зависимости,
делая тест быстрым, стабильным и сфокусированным.

**Где применяется в проектах:** тестирование сервисов с внешними зависимостями; проверка того, что
сервис правильно *использует* зависимость (вызвал нужный метод с нужными аргументами).

## Проблема: зависимость мешает тесту

```java
class OrderService {
    private final PaymentGateway gateway;     // ходит в платёжный шлюз по сети
    OrderService(PaymentGateway g) { this.gateway = g; }

    String pay(Order o) {
        return gateway.charge(o.total());     // реальный вызов — медленно и недетерминированно
    }
}
```

## Решение: мок зависимости

```java
@Test
void chargesTotal() {
    PaymentGateway gateway = mock(PaymentGateway.class);     // дублёр вместо реального шлюза
    when(gateway.charge(100)).thenReturn("OK");              // стаб: задаём поведение

    OrderService service = new OrderService(gateway);
    String result = service.pay(new Order(100));

    assertEquals("OK", result);
    verify(gateway).charge(100);                             // проверяем, что вызвали как надо
}
```

- `mock(...)` создаёт дублёр; по умолчанию методы возвращают `null`/`0`/пусто.
- `when(...).thenReturn(...)` — стаб: «когда вызовут так — верни это».
- `verify(...)` — проверка взаимодействия: метод действительно был вызван с этими аргументами.

## Типы дублёров

- **Stub** — отдаёт заранее заданные ответы (`when().thenReturn()`).
- **Mock** — стаб + проверка взаимодействий (`verify`).
- **Fake** — рабочая упрощённая реализация (например, in-memory репозиторий вместо БД).

## Что мокать, а что нет

Мокать стоит **внешние границы**: БД, HTTP-клиенты, очереди, часы/рандом. Не стоит мокать
value-объекты, коллекции, простую логику — это делает тест хрупким и бессмысленным (проверяешь мок,
а не код).

```java
// ❌ бессмысленно: мокать то, что можно просто создать
List<String> list = mock(List.class);
// ✅ просто создать
List<String> list = List.of("a", "b");
```

## Итог

**Что изучено:**
- Дублёры изолируют единицу от медленных/недетерминированных зависимостей.
- Mockito: `mock`/`when().thenReturn()`/`verify`; стаб vs мок vs fake.
- Мокать границы (БД, сеть), не мокать value-объекты и простую логику.

**Как применять на практике:**
- Проектировать зависимости как интерфейсы, чтобы их можно было подменить в тесте.
- Стабить ответы внешних систем; через `verify` проверять корректность взаимодействия.
- Для БД часто удобнее fake/Testcontainers, чем гора моков (см. соседнюю статью).
