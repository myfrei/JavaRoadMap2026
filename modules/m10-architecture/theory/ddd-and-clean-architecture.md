# DDD и чистая (гексагональная) архитектура

> Модуль 10 — Архитектура · [к модулю](../../../course/10-architecture.md)

## Зачем это нужно

Когда система растёт, бизнес-логика «растворяется» в контроллерах, SQL и фреймворке — менять её
становится страшно. DDD (Domain-Driven Design) и чистая архитектура ставят **домен** (бизнес-правила)
в центр и изолируют его от деталей (БД, веб, очереди). Результат: логику легко тестировать и менять,
а инфраструктуру — заменять.

**Где применяется в проектах:** сложные доменные системы (биллинг, логистика, финансы); проекты с
долгой жизнью; там, где важна тестируемость бизнес-логики.

## Главная идея: правило зависимостей

Зависимости направлены **внутрь**, к домену. Домен ничего не знает о БД и вебе:

```text
        ┌─────────────────────────────┐
        │  Инфраструктура (БД, HTTP)  │   ← детали, заменяемы
        │   ┌─────────────────────┐   │
        │   │   Приложение (use   │   │   ← сценарии (оркестрация)
        │   │   cases / сервисы)  │   │
        │   │   ┌─────────────┐   │   │
        │   │   │   ДОМЕН      │   │   │   ← бизнес-правила, без зависимостей
        │   │   └─────────────┘   │   │
        │   └─────────────────────┘   │
        └─────────────────────────────┘
```

Домен в центре не импортирует ни Spring, ни JDBC — только чистую Java.

## Порты и адаптеры (гексагональная)

Домен объявляет **порт** (интерфейс), а инфраструктура даёт **адаптер** (реализацию):

```java
// домен/приложение — ПОРТ (что нужно), без деталей
public interface OrderRepository {
    void save(Order order);
    Optional<Order> findById(long id);
}

// инфраструктура — АДАПТЕР (как именно), реализует порт
public class JdbcOrderRepository implements OrderRepository { /* SQL */ }
```

Сервис зависит от `OrderRepository` (порт). В тесте подставляем in-memory адаптер, в проде — JDBC.
Это инверсия зависимостей (DIP) в масштабе архитектуры.

## Кирпичики DDD

- **Entity** — объект с идентичностью (`Order` с id).
- **Value Object** — без идентичности, сравнивается по значению (`Money`, `Address` — `record`).
- **Aggregate** — кластер сущностей с одним «корнем», через который идут изменения (инвариант целого).
- **Bounded Context** — граница модели; в одном контексте «Заказ» одно, в другом — другое.
  Это естественные границы будущих микросервисов (модуль 8).

## Чем это окупается

- Бизнес-логику тестируешь без БД и веба — быстро и просто.
- Меняешь БД/фреймворк, не трогая домен.
- Код отражает язык бизнеса (ubiquitous language), его легче обсуждать с заказчиком.

> Цена — больше слоёв и интерфейсов. Для простого CRUD это оверкилл; ценность растёт со сложностью домена.

## Итог

**Что изучено:**
- Правило зависимостей: всё направлено внутрь, домен независим от деталей.
- Порты (интерфейсы домена) и адаптеры (реализации в инфраструктуре).
- Кирпичики DDD: Entity, Value Object, Aggregate, Bounded Context.

**Как применять на практике:**
- Держать бизнес-правила в чистом домене (без Spring/JDBC) и покрывать их быстрыми тестами.
- Объявлять порты в домене, реализации (БД/HTTP) — в инфраструктуре.
- Применять глубину DDD по сложности: для простого CRUD — не усложнять.
