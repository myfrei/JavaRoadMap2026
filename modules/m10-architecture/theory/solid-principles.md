# Принципы SOLID

> Модуль 10 — Архитектура · [к модулю](../../../course/10-architecture.md)

## Зачем это нужно

SOLID — пять принципов, делающих ООП-код гибким и поддерживаемым: его легко менять, расширять и
тестировать. Это не догма, а набор ориентиров против «спагетти», где изменение в одном месте ломает
пять других.

**Где применяется в проектах:** проектирование классов и модулей; код-ревью; рефакторинг легаси;
обоснование архитектурных решений.

## S — Single Responsibility (единственная ответственность)

У класса одна причина для изменения.

```java
// ❌ класс делает всё сразу — меняется по многим причинам
class UserService {
    void register(User u) { /* валидация + БД + отправка письма + лог */ }
}
// ✅ ответственности разделены
class UserRegistration {
    UserRegistration(UserRepository repo, Notifier notifier) { ... }
    void register(User u) { repo.save(u); notifier.send(u.email(), "Welcome"); }
}
```

## O — Open/Closed (открыт для расширения, закрыт для изменения)

Новое поведение добавляют **новым кодом**, не переписывая существующий:

```java
interface Discount { double apply(double price); }
record PercentDiscount(double pct) implements Discount {
    public double apply(double p) { return p * (1 - pct); }
}
// новая скидка = новый класс, старый код не трогаем
```

## L — Liskov Substitution (подстановка Лисков)

Наследник должен работать везде, где ожидается родитель, не ломая поведение. Классический анти-пример:
`Square extends Rectangle`, где `setWidth` неожиданно меняет высоту — подстановка ломается.

## I — Interface Segregation (разделение интерфейсов)

Лучше несколько узких интерфейсов, чем один «толстый». Клиент не должен зависеть от методов,
которые не использует.

```java
// ❌ interface Worker { work(); eat(); sleep(); } — робот не ест
// ✅ interface Workable { work(); }  interface Feedable { eat(); }
```

## D — Dependency Inversion (инверсия зависимостей)

Зависеть от **абстракций**, а не от конкретных классов. Высокоуровневая логика не должна знать про
JDBC или конкретный HTTP-клиент:

```java
class OrderService {
    private final OrderRepository repo;            // интерфейс, не JdbcOrderRepository
    OrderService(OrderRepository repo) { this.repo = repo; }
}
```

Это и есть основа DI из модуля 6.

## Итог

**Что изучено:**
- SRP (одна ответственность), OCP (расширять, не менять), LSP (корректная подстановка),
  ISP (узкие интерфейсы), DIP (зависеть от абстракций).

**Как применять на практике:**
- Делить классы по ответственностям; добавлять поведение новыми реализациями интерфейсов.
- Зависеть от интерфейсов (`Repository`, `Notifier`) — это даёт тестируемость и гибкость.
- Применять SOLID как ориентир, а не слепо: цель — простой изменяемый код, а не «принципы ради принципов».
