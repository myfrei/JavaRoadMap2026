# Как работает Java: JDK, JRE, JVM и байткод

> Модуль 0 — Фундамент · [к модулю](../../../course/00-fundamentals.md)

## Зачем это нужно

Это фундамент, на котором стоит всё остальное. Если не понимать, что происходит при запуске
программы, Java превращается в магию: непонятно, почему «работает на моей машине», откуда берутся
стектрейсы, зачем выбирать дистрибутив JDK и что значит «прогрев JIT».

**Где применяется в проектах:** выбор и установка JDK в команде и в CI; сборка Docker-образа
(там нужен именно JRE/JDK нужной версии); чтение стектрейсов; разговоры про производительность
(JIT, прогрев); понимание, почему один и тот же `.jar` запускается на Linux, macOS и Windows.

## Компиляция: исходник → байткод → исполнение

Java одновременно **компилируемый и интерпретируемый** язык. Исходник компилируется не в машинный
код процессора, а в **байткод** — промежуточное представление, которое исполняет JVM.

```java
// Hello.java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Привет, JVM!");
    }
}
```

```bash
javac Hello.java   # → Hello.class — это БАЙТКОД, а не программа под конкретный процессор
java Hello         # JVM загружает Hello.class, проверяет и исполняет
```

Что здесь важно:

- `javac` превращает `.java` в `.class`. Внутри — инструкции JVM (можно посмотреть `javap -c Hello`).
- `java` запускает **JVM**, которая загружает класс, проверяет байткод на корректность и исполняет.
- Байткод одинаков на всех ОС — поэтому «**write once, run anywhere**»: компилируешь один раз,
  запускаешь везде, где есть JVM.

## JIT: почему Java быстрая

JVM сначала интерпретирует байткод, а «горячие» (часто исполняемые) участки на лету компилирует
в нативный машинный код — это **JIT (Just-In-Time) компиляция**. Поэтому после «прогрева»
Java-код работает близко к скорости C++. Отсюда же эффект: первые вызовы метода медленнее последующих.

## JDK vs JRE vs JVM

Три слоя, которые часто путают:

| Сокращение | Что это | Что содержит |
|------------|---------|--------------|
| **JVM** | виртуальная машина | исполняет байткод, управляет памятью и GC |
| **JRE** | среда выполнения | JVM + стандартные библиотеки (`java.*`) |
| **JDK** | комплект разработчика | JRE + инструменты: `javac`, `jshell`, `jar`, `javadoc`, `jcmd` |

Простыми словами: **JDK** нужен, чтобы *писать и собирать* код; **JRE** — чтобы *запускать*.
В этом проекте тулчейн — **Java 25 LTS** (Gradle скачивает его автоматически).

## JShell — мгновенные эксперименты

В JDK есть REPL: можно проверять код без класса и `main`.

```bash
jshell
jshell> int x = 21 * 2
x ==> 42
jshell> "abc".repeat(3)
$2 ==> "abcabcabc"
```

Это лучший способ быстро проверить незнакомый метод стандартной библиотеки.

## Связь с кодом модуля

Метод [`Main.main`](../src/main/java/com/javaroadmap/m00/Main.java) — это та самая «точка входа»
`public static void main(String[] args)`, которую ищет команда `java`. Запусти его через Gradle:

```bash
./gradlew :modules:m00-fundamentals:run
```

Gradle под капотом делает то же самое: компилирует `.java` → `.class` тулчейном Java 25 и запускает JVM.

## Итог

**Что изучено:**
- Java компилируется в *байткод*, который исполняет *JVM* (отсюда кроссплатформенность).
- JIT компилирует горячий код в нативный — поэтому важен «прогрев».
- JDK = инструменты + JRE; JRE = JVM + библиотеки; JVM = исполнитель байткода.
- JShell — REPL для быстрых проверок.

**Как применять на практике:**
- Осознанно выбирать дистрибутив и версию JDK (Temurin, Java 25 LTS) для проекта, CI и Docker.
- Читать стектрейсы, понимая, что код исполняет JVM.
- Проверять незнакомые API в JShell за секунды, не создавая класс.
- Не делать выводов о производительности по первому запуску — дать JIT прогреться (см. модуль 11).
