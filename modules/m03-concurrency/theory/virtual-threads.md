# Виртуальные потоки и structured concurrency

> Модуль 3 — Конкурентность · [к модулю](../../../course/03-concurrency.md)

## Зачем это нужно

Классический поток ОС «тяжёлый» (~1 МБ стека), поэтому их не бывает миллионов — отсюда пулы и
сложный асинхронный код. **Виртуальные потоки** (Project Loom, стабильны с Java 21) дёшевы: их можно
создавать сотнями тысяч. Это позволяет писать простой **блокирующий** код, который масштабируется как
асинхронный.

**Где применяется в проектах:** серверы с тысячами одновременных соединений; задачи, которые много
ждут ввод-вывод (HTTP-вызовы, БД); замена сложных реактивных пайплайнов на читаемый последовательный код.

## Платформенный vs виртуальный поток

```java
// платформенный поток ОС — дорогой, их тысячи максимум
Thread platform = Thread.ofPlatform().start(() -> work());

// виртуальный поток — дешёвый, их могут быть миллионы
Thread virtual = Thread.ofVirtual().start(() -> work());
```

Виртуальный поток исполняется на пуле «несущих» потоков ОС: когда он блокируется на I/O, JVM
**снимает** его с несущего потока и ставит другой. Поток ОС не простаивает.

## 100 000 задач — без проблем

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 100_000; i++) {
        executor.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1));   // «блокирующий» вызов — но это ОК
            return null;
        });
    }
}   // дождётся все 100 000 виртуальных потоков
```

С платформенными потоками такой код упал бы по памяти. С виртуальными — нормальная практика:
один виртуальный поток на задачу.

## Structured concurrency

Когда задача порождает подзадачи, хочется управлять ими как единым целым: дождаться всех,
а при ошибке одной — отменить остальные. Для этого `StructuredTaskScope`:

```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var user  = scope.fork(() -> fetchUser(id));     // подзадача 1
    var order = scope.fork(() -> fetchOrder(id));    // подзадача 2
    scope.join();                                    // ждём обе
    scope.throwIfFailed();                           // если одна упала — отменить вторую и пробросить
    return new Dashboard(user.get(), order.get());
}
```

Подзадачи живут не дольше своего scope — нет «утёкших» потоков, ошибки и отмена распространяются
предсказуемо.

## Когда это НЕ серебряная пуля

Виртуальные потоки выигрывают на **I/O-bound** нагрузке (много ожидания). Для чисто
**CPU-bound** вычислений параллелизм всё равно ограничен числом ядер — там по-прежнему уместен
`fixedThreadPool` или Fork/Join.

## Итог

**Что изучено:**
- Виртуальные потоки дёшевы — «один поток на задачу» снова работает.
- JVM снимает виртуальный поток с несущего на время блокировки I/O.
- `StructuredTaskScope` управляет подзадачами как единым целым (join + отмена при ошибке).

**Как применять на практике:**
- Для I/O-тяжёлых серверов писать простой блокирующий код на виртуальных потоках вместо реактивщины.
- Использовать `newVirtualThreadPerTaskExecutor()` для массы независимых задач.
- Оставлять пулы фиксированного размера для CPU-bound вычислений.
