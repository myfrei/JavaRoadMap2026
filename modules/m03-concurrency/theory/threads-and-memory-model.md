# Потоки и модель памяти Java (JMM)

> Модуль 3 — Конкурентность · [к модулю](../../../course/03-concurrency.md)

## Зачем это нужно

Многопоточность даёт параллелизм, но приносит коварные баги: гонки данных (race conditions),
когда два потока меняют общее состояние и результат зависит от удачи. Понимание модели памяти Java
(JMM) — это разница между «работает на тестах, падает в проде» и надёжным кодом.

**Где применяется в проектах:** серверы (каждый запрос — поток); счётчики и метрики; кэши; любые
общие изменяемые данные под нагрузкой.

## Гонка данных

```java
class Counter {
    private int value = 0;
    void increment() { value++; }     // НЕ атомарно: чтение -> +1 -> запись
    int value() { return value; }
}
```

`value++` — три операции. Если 8 потоков по 1000 раз вызовут `increment()`, итог почти наверняка
будет **меньше** 8000: потоки затирают обновления друг друга. Это гонка.

## Решение 1: synchronized

`synchronized` гарантирует, что в блок входит только один поток, и устанавливает отношение
**happens-before** (изменения одного потока видны другому).

```java
class SafeCounter {
    private int value = 0;
    synchronized void increment() { value++; }   // взаимное исключение + видимость
    synchronized int value() { return value; }
}
```

## Решение 2: атомики (быстрее, без блокировок)

Для счётчиков лучше `AtomicInteger` — он использует аппаратный CAS (compare-and-swap), без
блокировки потока:

```java
import java.util.concurrent.atomic.AtomicInteger;

AtomicInteger value = new AtomicInteger();
value.incrementAndGet();           // атомарно
// после 8 потоков по 1000: ровно 8000
```

## Видимость и volatile

Без синхронизации поток может не увидеть изменения, сделанные другим (из-за кэшей процессора и
оптимизаций). `volatile` гарантирует видимость записи для всех потоков:

```java
private volatile boolean running = true;   // флаг остановки, видимый всем потокам
public void stop() { running = false; }
```

`volatile` обеспечивает **видимость**, но не атомарность составных операций (`value++` всё равно
небезопасен с `volatile`).

## happens-before — главное правило JMM

Если действие A *happens-before* B, то эффекты A видны в B. Эту связь дают `synchronized`,
`volatile`, `Atomic*`, запуск/join потока. Без неё компилятор и процессор вправе переупорядочить
операции, и вы получите «невозможные» баги.

## Итог

**Что изучено:**
- Гонка данных на примере `value++`; почему теряются обновления.
- `synchronized` (взаимное исключение + видимость) и атомики (CAS, без блокировок).
- `volatile` даёт видимость, но не атомарность; правило happens-before.

**Как применять на практике:**
- Защищать любое общее изменяемое состояние (`synchronized`/атомики/конкурентные коллекции).
- Для счётчиков и флагов брать `Atomic*`/`volatile` вместо тяжёлых блокировок.
- Тестировать конкурентный код под нагрузкой (много потоков, много итераций) — баг проявляется не всегда.
