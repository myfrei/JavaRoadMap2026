# Отказоустойчивость: circuit breaker, retry, timeout

> Модуль 8 — Микросервисы · [к модулю](../../../course/08-microservices.md)

## Зачем это нужно

В распределённой системе сбои — норма, а не исключение: сеть моргает, сервисы тормозят и падают.
Без защиты один медленный сервис «затягивает» вызывающих, и отказ каскадом валит всю систему.
Паттерны отказоустойчивости локализуют сбой и дают системе деградировать мягко.

**Где применяется в проектах:** любые межсервисные вызовы; обращения к внешним API; работа с БД и
очередями под нагрузкой. В Java — библиотека Resilience4j.

## Timeout — никогда не ждать вечно

```java
// ❌ без таймаута поток зависнет навсегда, если сервис не отвечает
String r = httpClient.get(url);

// ✅ ограничиваем ожидание
var request = HttpRequest.newBuilder(URI.create(url))
        .timeout(Duration.ofSeconds(2))      // не ждём дольше 2 сек
        .build();
```

Зависшие потоки — топливо для каскадных отказов. Таймаут есть всегда и везде.

## Retry с экспоненциальным backoff

Временные сбои лечатся повтором, но с нарастающей паузой, чтобы не добивать упавший сервис:

```java
long delay = baseMs * (1L << attempt);   // 100, 200, 400, 800...
```

Важно: повторять только **идемпотентные** операции (`GET`, `PUT`), иначе ретрай `POST` создаст
дубликат (см. идемпотентность в модулях 14/21).

## Circuit breaker — «предохранитель»

Если сервис стабильно падает, бессмысленно долбить его и копить зависшие запросы. Автомат с тремя
состояниями размыкает цепь:

```text
CLOSED  --(N ошибок подряд)-->  OPEN  --(пауза)-->  HALF-OPEN  --(успех)-->  CLOSED
  ^                                                      |
  пропускает запросы          сразу отклоняет        пробует один запрос
```

```java
class CircuitBreaker {
    private int failures;
    private boolean open;
    private final int threshold;

    boolean allowRequest() { return !open; }            // OPEN -> сразу отказ, без вызова
    void recordFailure()   { if (++failures >= threshold) open = true; }
    void recordSuccess()   { failures = 0; open = false; }
}
```

В состоянии OPEN вызывающий мгновенно получает отказ (или fallback), не тратя время на заведомо
мёртвый сервис — это и останавливает каскад.

## Fallback и bulkhead

- **Fallback** — запасной ответ при сбое (кэш, заглушка, «сервис временно недоступен»).
- **Bulkhead** — изоляция ресурсов (отдельные пулы потоков на разные зависимости), чтобы сбой одной
  не выел потоки у всех.

## Итог

**Что изучено:**
- Сбои в распределёнке — норма; без защиты они каскадируют.
- Timeout, retry с backoff (только для идемпотентных операций), circuit breaker (CLOSED/OPEN/HALF-OPEN).
- Fallback и bulkhead для мягкой деградации и изоляции.

**Как применять на практике:**
- Ставить таймаут на каждый сетевой вызов — без исключений.
- Оборачивать межсервисные вызовы в circuit breaker + retry (Resilience4j).
- Готовить fallback и изолировать пулы, чтобы один сбой не положил весь сервис.
