# Асинхронные сообщения, saga и outbox

> Модуль 8 — Микросервисы · [к модулю](../../../course/08-microservices.md)

## Зачем это нужно

Синхронные вызовы связывают сервисы: если один недоступен, падает и второй. Асинхронные сообщения
(через брокер) развязывают их во времени — отправитель не ждёт получателя. Но без общей транзакции
встаёт вопрос: как держать данные согласованными между сервисами? Ответ — saga и outbox.

**Где применяется в проектах:** событийная архитектура; интеграции, где не нужен мгновенный ответ;
бизнес-процессы, охватывающие несколько сервисов (заказ → оплата → доставка).

## Синхронно vs асинхронно

- **Синхронно** (REST/gRPC): простой запрос-ответ, но временна́я связанность — нужен живой получатель.
- **Асинхронно** (Kafka/RabbitMQ): отправитель публикует событие и идёт дальше; получатель обработает,
  когда сможет. Слабая связанность, буферизация всплесков, но сложнее отлаживать.

```text
[Заказы] --"OrderCreated"--> [брокер] --> [Платежи]
                                       --> [Уведомления]   (несколько подписчиков)
```

## Распределённая транзакция = saga

Одной транзакции БД на несколько сервисов нет. Saga — это последовательность локальных транзакций,
где каждый шаг при сбое **компенсируется** обратным действием:

```text
1. Заказ: создать (NEW)        ─┐
2. Платёж: списать деньги        │  если шаг 3 упал ->
3. Склад: зарезервировать товар ─┘  компенсации: вернуть деньги, отменить заказ
```

```java
try {
    orders.create(order);          // шаг 1
    payment.charge(order);         // шаг 2
    inventory.reserve(order);      // шаг 3
} catch (Exception e) {
    payment.refund(order);         // компенсация шага 2
    orders.cancel(order);          // компенсация шага 1
}
```

Saga даёт **итоговую согласованность** (eventual consistency): система приходит в согласованное
состояние не мгновенно, но гарантированно.

## Проблема двойной записи и outbox

Опасный момент: «сохранили заказ в БД, но не смогли отправить событие в брокер» (или наоборот) —
данные рассинхронизированы. Паттерн **outbox** решает это:

```text
В ОДНОЙ транзакции БД:
  - INSERT в таблицу orders
  - INSERT события в таблицу outbox
Отдельный процесс читает outbox и публикует события в брокер (с ретраями).
```

Раз запись в `outbox` идёт в той же транзакции, что и бизнес-данные, — событие не потеряется и не
уйдёт без сохранённых данных.

## Итог

**Что изучено:**
- Асинхронные сообщения развязывают сервисы во времени (ценой сложности отладки).
- Saga = локальные транзакции + компенсации; итоговая согласованность.
- Outbox решает проблему двойной записи «БД ↔ брокер».

**Как применять на практике:**
- Использовать события там, где не нужен синхронный ответ, — это повышает устойчивость.
- Для процессов через несколько сервисов проектировать saga с компенсациями, а не мечтать о 2PC.
- Публиковать события через outbox; получателей делать идемпотентными.
